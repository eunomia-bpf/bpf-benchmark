# bpfopt testbin: per-prog reproducer corpus

Date: 2026-05-10

## What this is

542 BPF program inputs dumped from the corpus framework, organized per app/prog.
Use these to debug bpfopt passes locally on the host **without running KVM corpus**.

## Source

Generated by:
1. Patching `runner/config/passes/noop/default.yaml` to append `&& false`
2. Patching `daemon/src/commands.rs::MAX_FAILURE_ARTIFACTS_PER_REQUEST` from 32 → 10000
3. Running `BPFREJIT_BENCH_PASSES=noop KEEP_WORKDIRS=1 SAMPLES=1 WORKLOAD_DURATION=10 make corpus`
4. Extracting all `failure-artifacts/<prog_id>.tar.gz` per app

The patches are reverted after the dump; this directory is the only persistent artifact.


## Usage: run a pass on a testbin entry

Standard CLI invocation matching what daemon does:

```sh
target/debug/bpfopt --pass <name> \
    --input bpfopt/testbin/<app>/<prog_id>_<name>/canonicalize_output.bin \
    --output /tmp/test_out.bin \
    --report /tmp/test_report.json \
    --prog-type <prog_type>
```

For kinsn passes that need `--target`, see "Augmenting with target.json" below.

## Augmenting with target.json (for kinsn passes)

The noop dump only ran `noop`, which doesn't need `--target`. To run kinsn passes
(rotate / cond_select / ccmp / extract / endian_fusion / bulk_memory / prefetch),
you need a `target.json` describing kinsn capabilities. Example from a previous
multi-pass run is at `/tmp/dce_target.json` (preserved during P1-F invest).

To get a fresh target.json, run a multi-pass corpus with one prog and KEEP_WORKDIRS=1,
e.g. `BPFREJIT_BENCH_PASSES=noop,rotate KEEP_WORKDIRS=1 ...`.

## Coverage

542 / 542 = 100% of all live BPF programs in the 7-app corpus on x86_64 KVM.

## Notes

- These are **pre-rejit baseline** bytecodes (post-canonicalize, pre-any-optimization).
- Use these as input to test individual pass behavior, byte-identical regression checks,
  or to extract minimal reproducer for verifier-rejection bugs.
- After modifying bpfopt source, run any pass on the relevant testbin entry to verify
  byte-identical output / new behavior — much faster than full KVM corpus.
- The data is committed to git so it's available across machines without re-running corpus.
