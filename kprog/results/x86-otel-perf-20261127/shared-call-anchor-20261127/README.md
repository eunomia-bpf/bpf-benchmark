# Keep branches entering expanded helper calls

The frozen-scalar compiler merges OTel's normal unwind handoff into one shared bpf_tail_call site. A source branch targets the call itself. Native-link previously replaced the call with instructions having only synthetic addresses, so its branch-remapping pass chose the next original instruction, skipping the entire tail expansion. In the captured entry, argument setup at0x64f was followed by JMP0x6cb (return) while the actual tail expansion began0x672. The fault is common to branches entering expanded helpers, not an app-specific policy.

The first instruction in each primary expansion now retains the original call's address in both instruction IP and origin metadata. Later instructions remain synthetic; postprocessing of an already anchored call remains synthetic. This covers tail calls, current-task/CPU helpers and array expansions with the same rule. No new flag, app/program selector, compiler policy, kernel or benchmark change.

Release build and all13tests pass. The regression tests unconditional and conditional branches entering an expanded call, requiring the target to be the expansion rather than the following RET. Actual captured P plus its plan also links successfully: entry blob2822bytes. The full linked-entry host test uses this kernel's actual per-CPU ABI and tail-count/stack layout, a populated slot1 and count0. Before repair it returned-1 without transfer/count increment; after repair it reaches the target with count1, exact context, stack and BPF frame preserved (sentinel777). Missing-map and empty-tail cases still return0/-1. This is a meaningful code/ABI regression, not whole-application performance evidence.

Read-only guest snapshots from profile200824 establish matching initial stress-PID map hits, populated native program-array slot1, zero native unwind attempts/frames, zero-frame native records and one requested tail per record, versus deep baseline stacks and growing frame counters. Those observations and the actual branch prove skipped work behind the earlier11.938x and this9.494x diagnostics. Data and app-ok receipts remain preserved; these ratios are not equal-work gains.
