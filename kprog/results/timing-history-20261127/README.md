## 看了什么

- `scan.py` 读 corpus/results 下全部 completed 且 stats 开的运行（x86 KVM 1311 行，2026-05-22 到 11-27；另有 x86 docker 424 行、arm64 QEMU 90 行、AWS arm64 58 行），每个应用每次运行算两边每次调用：eBPF = baseline 一段 run_time_ns 之和 / run_cnt 之和，原生 = post_rejit 一段同样算，比值 = eBPF / 原生。结果在 `all-runs.tsv`。
- `summarize.py` 按应用、运行类别（full = 3 × 180 秒的冻结默认设置，10s = make check 的 1 × 10 秒）、日期取中位，结果在 `by-day.tsv`。
- arm64 的完整计时在 Spark 上跑，原始数据在 kprog-raw，数字取自 kprog/results/arm64-spark-run5..8 的 README。
- 这里的比值是所有程序合在一起的每次调用；05-29 冻结表里的“05-29 per call”出自 05-29 的解析器，算法是逐程序的几何平均，两种算法的数字分开看。

## 消失的“好数字”是缺陷

| 数字 | 原因（收据） |
|---|---|
| OTel 14–19x（5 月、11-10 到 11-16） | 原生一侧读的是公开的 perf-event 布局，内核传的是 bpf_perf_event_data_kern，原生在展开栈之前就返回；展开次数 913,099,438 → 0（perf-history-review-20261120，equal-work-20261113）；95cb987c5 修好之后两边做同样的工作，比值回到 0.93–0.98x |
| Cilium 3.3–4.6x（11-10 到 11-16、11-19） | 原生按 Cilium 的示例配置编译，替换了 agent 用自己的常量编出的程序；11-19 原生的包还走了 cil_to_host，发包端多推了约 3 倍的包（best-numbers-20261121，协调者 2026-11-19T21:30:54Z）；改成 agent 自己的编译开关之后，比值回到 1.1–1.25x |
| Cilium 0.46x（11-22） | x86 链接器丢了 jiffies_64 的 GOT 读，时钟读到旧寄存器；dcf4a1aef 修好，11-23 回到 1.2x |
| Katran 1.19–1.34x（05-29、11-11 到 11-14） | 旧链接器按调用顺序给查找点配目标，三处 LRU 查找绑错；修好之后原生从 142–147 ns 回到 175–177 ns，比值 1.00–1.04x |

这几个数字下降，是因为原生一侧改成和 eBPF 做同样的工作；修好之后量到的是真实的比值。

## 结论

1. 看上去“越来越慢”的主要原因：以前的大数字（OTel 15x、Cilium 4x、Katran 1.25x）来自原生一侧少做了工作，修好之后量到的是真实比值。
2. 修好之后，x86 每次调用从 11-20 到 11-24 的完整计时里，BCC、Tetragon、Tracee、Katran、OTel 持平或上升，Cilium 从 1.11x 升到 1.25x；arm64 run 5 → run 8 五个应用上升。
3. 和本周最好的比，Cilium、Katran 低一些；10 秒检查的波动很大，单次的数只作诊断。
4. 离目标（每次调用至少快 20%）差得最多的是 OTel（0.98x）、BCC（1.02x）、Katran（1.04x），arm64 上还有 Cilium（1.02x）。按 runtime-profile-20261120 的采样，这几个应用的热路径以 helper、时钟和 map 操作为主，原生和 JIT 做的是同样的调用，差距要靠 helper 内联和 map 查找的绑定去拿；这是 perf 现在的第一项（todo 第 0 节，协调者 2026-11-27T18:51Z）。
