Class F: B's frame exceeds the verifier's 512-byte stack.
  "invalid write to stack R10 off=-560..-952", 38 occurrences across the
  two apps: -856 x10, -888 x10, -800 x6, -864 x3, -952 x2, -768 x2,
  then -880, -704, -648, -584, -560 one each.

  Cause, measured, in two steps.

  B's own bytes are the ones the verifier refuses. Tetragon request 10's
  B opens with `0: r0 = 0` and `1: *(u64 *)(r10 - 0x358) = r0` (0x358 is
  856), which is exactly the log's
  "invalid write to stack R10 off=-856 size=8" after "processed 2 insns".
  That B is 153,099 instructions and needs a 1408-byte frame, so the
  emitter lays out a frame the guest kernel refuses: MAX_BPF_STACK is 512
  (vendor/linux-framework/include/linux/filter.h:99), enforced by
  check_stack_slot_within_bounds (verifier.c:7583) for writes and by the
  per-subprogram depth sum at :6772. The guest image is 7.0.0-rc2, which
  carries "combined stack size of %d calls is %d" and no private-stack
  mode, so subprogram frames sum to 512.

  The frame breaks into four parts, all measured on request 10's object
  and its generated C:
    union x86_sim_stack_mem                      224 B  (X86_SIM_STACK_BYTES 224U)
    __u8 __x86_stack_value_tags[28]                28 B  (one byte per 8-byte word)
    void *__x86_stack_value_ptrs[28]              224 B  (one pointer per word)
    register cells, ABI copies and spills          932 B
  The emulated stack is declared as a local by X86_SIM_L_DECLARE_STACK
  (kprog/x86/x86_sim_local_bpf.h:524-525) and the two side arrays by
  X86_SIM_L_DECLARE_STACK_VALUES (:336-338), so the first three rows,
  476 B, are unavoidable frame for a program with any stack at all. The
  remaining 932 B is what pushes this object past 512: request 1, which
  verifies, declares 56 U of stack and its whole object stays at 88 B.

  The layout itself caps the emulated stack before any spill. The three
  locals cost 2.125 x S for S bytes of stack the program touches
  (S for the union, S/8 for the tag bytes, S for the pointer word), so
  the verifier's 512-byte limit admits at most 241 bytes of emulated
  stack with nothing else in the frame. The ten requests at 1736 touch
  304 bytes and the 1408 group touches 224, so both the side arrays and
  the spills have to shrink, or the stack has to leave the frame.

  Why clang accepts it: B is compiled with `-mllvm -bpf-stack-size=4096`
  (kprog/x86/trusted_specializer.py:35 and :104), four times the
  verifier's limit, so nothing in the build stage reports the overflow.

  What remains to decide is the frame layout in B (spilling less around
  the emulated stack, or moving that union to a map value or a global),
  rather than the bound itself. The pointer words are load-bearing, not
  dead weight: a TAG_STACK word recovers its provenance only through them
  (X86_SIM_L_SV_READ_ONE, :368-371), so shrinking them means enumerating
  fewer words, which the sparse-stack-cache result already did for the
  arena cells -- a retained Tetragon render dropped from 53 cells to 16
  with the same 424-byte arena
  (kprog/results/sparse-stack-cache-20261119/README.md, PERF
  2026-11-19T18:45:59Z). That render's full B was never compiled, so
  carrying the same enumeration into the frame's side arrays is the open
  continuation.

  Scope, measured on the archived Tetragon capture: 23 of the 61 B
  objects that carry both the generated C and the object reach past 512
  bytes of frame. The frames cluster: ten objects reach 1736 (requests
  15, 18, 28, 30, 43, 48, 59, 70, 79 and 82, each with 304 bytes of
  emulated stack), ten reach 1408 with 224 (request 10 among them), two
  reach 1120 with 208 and one reaches 944. One object with a larger
  declared stack stays small: request 3 declares 320 bytes, never touches
  the emulated stack in its code, and its frame is 408, so the cost
  follows the stack the program actually uses. The pointer-

  "R* invalid mem access 'scalar'", 46 occurrences (Tetragon 32 across
  its 3 attempts, Tracee 14). 44 share one shape: load kprog_unspec's
  u64 word, test one bit, then dereference the loaded value:
    tetragon 3  insn 27-30: r2 = *(u64 *)(r2+0); r2 &= 1;

    tracee   3  insn 10-13: r2 = *(u64 *)(r7+0); r2 &= 1;
                            if r2 != 0 goto +13; r2 = *(u32 *)(r0+0)
  The other two (tetragon 5 and tetragon3 4, the same program) are
  "181: r0 = 0; 182: *(u64 *)(r0 +0) = r0" — a store through a zero
  scalar base, the RIP-relative absolute-address form the load macro
  comments on, which the verifier refuses as a scalar store.
  The x86 really loads through the address the application computed, and
  B reads that slot with kprog_x86_mem_load_fixed_into
  (kprog/formal/generated/x86_mem_access.h:86-104), whose BPF arm per
  width is bpf_probe_read_kernel at :93, :96, :99 and :102 followed by a
  re-read of the destination, and whose exported entry is
  KPROG_X86_MEM_LOAD (:173). The helper leaves a scalar, so the loaded 8
  bytes arrive at B with no provenance; the emulated pointer tag survives
  in the simulator's tags, and the verifier cannot see it. A store
  through such a value is the zero-base case above; a load through it is
  class G.
  This is the same root as class A (a helper's integer result
  dereferenced), but reached through B's own load path rather than
  through bpf_get_current_task, so the class-A fix does not cover it.
  The pointer-launder pass (kprog/x86/packet_bounds_ir.cpp:370-500)
  rewrites frame-pointer differences and a pointer-typed minuend; it does
  not give a loaded scalar pointer provenance.

  The simulator already knows the provenance it loses here. A 64-bit
  store into the emulated stack records the tag and the pointer
  (X86_SIM_L_STACK_VALUES_SAVE, x86_sim_local_bpf.h:360-364, into the
  side arrays at :326-346), and a load consults them
  (X86_SIM_L_STACK_VALUES_READ, :372-375). Both preserve the tag, so a
  pointer stored into the emulated stack and read back keeps its
  provenance. The failing sites read memory outside that stack (the
  kprog_unspec region and the zero-base RIP-relative slot), where the
  only read path is the probe-read helper. A fix therefore has to carry
  the tag across the same helper: read the value and its tag as the save
  and read pair do, and re-materialize the pointer with
  KPROG_PTR_ADD64_BITS instead of handing the verifier a scalar.
