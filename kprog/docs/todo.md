## 二、系统设计（kprog/docs/design.md“核心思想”“编译流水线”）

1. **P 的来源**：从应用源码直接编成机器码（“不是直接出机器码吗? 为啥变成这样了”，11-14）。
   - 源码尽量不改，必要时改一点（11-13、11-15）。
   - 兼容靠头文件（“不允许放进编译过程, 不是用头文件兼容吗”，11-15）。
   - 编译参数所有应用统一，固定 O3（11-15、11-21）。
2. **验证**：受保护的服务把忠实解释器 I 特化到 P，编成直线 eBPF B，交库存 verifier。接受就确证 P 内存安全。eBPF 只被分析，不执行。
3. **顺序**：“应该是先优化, 再验证优化后的那一份, 再优化, 再链接时优化.”（11-14）
4. **链接时优化**：verifier 接受后，对同一份被检查过的程序做这些事，再编成原生代码由内核直接执行：
   - 绑定 map 和 helper；
   - 就地内联 map 查找和 helper；
   - 折叠冻结的 .rodata；
   - 整体优化。

   原话：“inline map / helper 这个就是链接”；“没有额外的 受信改写, 只有 LTO”（11-14）。
5. **两种配置**：LTO 配置（验证加 LTO，主配置）和直接原生配置（对照），分别报告。
6. **运行的程序**：在运行的程序都是原生（“任何情况下绝对不允许留在 ebpf 上面跑”，11-21；“库的特性探测程序无所谓, 但是在运行的必须是原生.”，11-22）。
7. **起点和预算**：在 5/29 基础上，除了 verify 的部分，整个路径 1000 行以内的修复和优化；verify 和功能的部分完整保留（11-21）。
8. **规模**：一个工作树、一个内核、一个镜像、一个底座（11-11）。

## 三、要的优化（原话）

1. map 查找像 JIT 一样内联：“必须支持, 改 linker 或者或者在源代码的时候内联”（11-14）。
2. 内联之后常量消除：“helper map 也可以这样内联之后常量消除”（11-11）。
3. helper 用 C 编进去：“手写的 helper 例程 是不是应替换成 c 实现的直接编译进去的”（11-19）。
4. 读内核内存直接解引用（11-19）。
5. 去掉内核里不必要的检查，确保内联生效（11-16）。
6. 只做设计之内的：“设计之内的优化是不是必须在? 但不能任何额外的 check/guard? 这些优化是不是直接用 C 写在头文件里面的?”；“如果符合设计的优化应该保存, 不符合设计的不应该做, 也不需要调参. 不应该对比工作量.”（11-22）
7. 目标：
   - 每次调用至少快 20%；
   - 吞吐至少好 30%；
   - 原生快 50%、代码量减半（11-21 起“不需要调代码大小了”）；
   - “你应该无论如何比 kinsn 好得多”；
   - “任何都不应该更慢对吧?”
