## Fix

`runner/config/passes/dce/default.yaml` now passes the runner-provided target
metadata to `bpfopt`:

```yaml
command: |
  timeout 6000 bpfopt --pass dce --input ${INPUT} --output ${OUTPUT} --report ${REPORT} --prog-type ${PROG_TYPE} --target ${TARGET}
```

This is required after the first-round P1-F fix because `DcePass` now uses
`LivenessAnalysis::run_with_kinsn_registry()` through `PassContext`.
Kinsn-aware liveness needs the target JSON to resolve packed sidecar + kinsn
call pairs such as `bpf_select64`.

## Const Prop failed_rejit investigation

This was read-only investigation only; no `const_prop` code was changed.

Artifacts inspected:

- `corpus/results/x86_kvm_corpus_20260510_085438_783442/details/failure-artifacts/13.tar.gz`
- `corpus/results/x86_kvm_corpus_20260510_085438_783442/details/failure-artifacts/14.tar.gz`

Both failures happen at the `const_prop` step:

- prog 13 `perf_unwind_v8`: `const_prop` applied 31 `const_prop_alu_materialized` sites, then ReJIT failed.
- prog 14 `perf_unwind_dotnet`: `const_prop` applied 14 `const_prop_alu_materialized` sites, then ReJIT failed.

The concrete failure shape is consistent across both programs. Before
`const_prop`, the accepted step6 verifier log has a valid helper memory
argument:

```text
prog 13:
2501: (bf) r1 = r10                   ; R1=fp0
2502: (07) r1 += -64                  ; R1=fp-64
2503: (b7) r2 = 16
2504: (85) call bpf_probe_read_user#112

prog 14:
3741: (bf) r1 = r10                   ; R1=fp0
3742: (07) r1 += -16                  ; R1=fp-16
3743: (b7) r2 = 16
3744: (bf) r3 = r8
3745: (85) call bpf_probe_read_user#112
```

After `const_prop`, the failed step7 verifier log shows the pointer arithmetic
instruction replaced by a scalar materialization:

```text
prog 13:
2502: (bf) r1 = r10                   ; R1=fp0
2503: (b7) r1 = 0                     ; R1=0
2504: (b7) r2 = 16
2505: (85) call bpf_probe_read_user#112
R1 type=scalar expected=fp, pkt, pkt_meta, map_key, map_value, mem, ringbuf_mem, buf, trusted_ptr_

prog 14:
3742: (bf) r1 = r10                   ; R1=fp0
3743: (b7) r1 = 1                     ; R1=1
3744: (b7) r2 = 16
3745: (bf) r3 = r8
3746: (85) call bpf_probe_read_user#112
R1 type=scalar expected=fp, pkt, pkt_meta, map_key, map_value, mem, ringbuf_mem, buf, trusted_ptr_
```

Root-cause direction for a separate fix: `const_prop_alu_materialized` is
materializing an ALU operation on a pointer-typed register, turning a frame
pointer argument (`fp-64` / `fp-16`) into a scalar immediate before
`bpf_probe_read_user`. The likely guard is to reject ALU materialization when
the destination's verifier type is pointer-like, even if the verifier state has
an exact scalar-looking value for some path. This needs its own fix and test.
