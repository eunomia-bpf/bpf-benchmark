## A. `reg_known_stack_bytes`

`BBProgram::reg_known_stack_bytes` has the right public shape: it takes only
`InsnSite`, a register number, and a byte width, and returns `Option<Vec<u8>>`
at `bpfopt/crates/bpfopt/src/analysis/bbprogram.rs:328-335`. It does not expose
`RegState`, `StackState`, or `VerifierInsn` to callers.

The implementation is a proper typed wrapper over verifier state:

- It reads verifier snapshots through the private `verifier_states_at` helper at
  `bpfopt/crates/bpfopt/src/analysis/bbprogram.rs:306-307`.
- It rejects missing/empty/edge-full states at
  `bpfopt/crates/bpfopt/src/analysis/bbprogram.rs:336-343`.
- It requires the requested register to be an fp-relative pointer and extracts
  the same concrete stack byte vector from every state at
  `bpfopt/crates/bpfopt/src/analysis/bbprogram.rs:345-356`.
- The raw verifier decoding stays private to BBProgram helpers:
  fp-offset extraction at `bpfopt/crates/bpfopt/src/analysis/bbprogram.rs:968-975`,
  byte-vector extraction at `bpfopt/crates/bpfopt/src/analysis/bbprogram.rs:977-993`,
  stack-slot byte interpretation at `bpfopt/crates/bpfopt/src/analysis/bbprogram.rs:995-1027`,
  and slot exact-byte extraction at `bpfopt/crates/bpfopt/src/analysis/bbprogram.rs:1028-1030`.

Residual raw verifier surface remains outside this API: `PassContext` still stores
`pub(crate) verifier_states: Arc<[VerifierInsn]>` at
`bpfopt/crates/bpfopt/src/pass.rs:454-459`, and `VerifierInsn` /
`VerifierInsnKind` are still crate-re-exported at `bpfopt/crates/bpfopt/src/pass.rs:21`.
That is the same broad lift-boundary smell R3 called out, but
`reg_known_stack_bytes` itself hides the raw types correctly.

## B. Hint Type Consolidation

There is exactly one final resolved map-inline hint type in current
`map_inline.rs`: `ResolvedMapInlineHint` at
`bpfopt/crates/bpfopt/src/passes/map_inline.rs:488-496`, with `ResolvedHintMap`
only as a collection alias at `bpfopt/crates/bpfopt/src/passes/map_inline.rs:497`.
Old names such as `BoundaryResolved*`, `ResolvedInline*`,
`KeyExtractionError`, and `SiteRewriteError` have no hits in the reviewed files.

The side-input flow is coherent but not literally "main.rs creates
`ResolvedMapInlineHint` during lift":

- `main.rs` parses CLI hints into external `MapInlineHintSpec` at
  `bpfopt/crates/bpfopt/src/main.rs:855-868` and attaches them to
  `PassContext` at `bpfopt/crates/bpfopt/src/main.rs:771-786`.
- `main.rs` then calls `lift_with_pass_context` at
  `bpfopt/crates/bpfopt/src/main.rs:313`.
- The lift boundary converts external PC anchors into pass-local site anchors in
  `resolve_map_inline_hints` at
  `bpfopt/crates/bpfopt/src/analysis/bbprogram_lift.rs:187-200` and
  `bpfopt/crates/bpfopt/src/analysis/bbprogram_lift.rs:230-264`.
- The map-aware resolved form is created inside the pass after `map_info` exists:
  `resolve_inline_hints` at `bpfopt/crates/bpfopt/src/passes/map_inline.rs:647-678`
  and `insert_resolved_hint` pushing `ResolvedMapInlineHint` at
  `bpfopt/crates/bpfopt/src/passes/map_inline.rs:939-1011`.

This is the right ownership split: main owns CLI/IO, lift owns PC-to-site
translation, and map_inline owns map-aware hint resolution.

## E. Coherence

The simplified file is still large, but it now reads as a focused pass rather
than a framework leak. The main responsibilities are pass-specific: map lookup
site discovery, verifier-guided key extraction, hint resolution, direct
pseudo-map-value constantization, R0 use classification, and replacement/deletion
emission.

Five largest current functions in `map_inline.rs`:

1. `run_map_inline_round`, `bpfopt/crates/bpfopt/src/passes/map_inline.rs:1142-1543`
   (402 LOC): one round's orchestration, including map info refresh, direct-load
   rewrites, lookup classification, skip recording, conflict detection, and edit
   application.
2. `classify_r0_uses_with_options`,
   `bpfopt/crates/bpfopt/src/passes/map_inline.rs:2583-2699` (117 LOC): follows
   R0 aliases after a lookup and classifies null checks, fixed-offset loads,
   alias copies, helper calls, and other uses.
3. `build_direct_map_value_load_rewrites`,
   `bpfopt/crates/bpfopt/src/passes/map_inline.rs:1988-2088` (101 LOC): rewrites
   direct pseudo-map-value loads to scalar constants when the snapshot value is
   available and safe.
4. `build_site_rewrite`, `bpfopt/crates/bpfopt/src/passes/map_inline.rs:1721-1815`
   (95 LOC): reads the snapshot value, prepares per-CPU values, determines which
   lookup/null-check/setup sites can be deleted, and emits scalar load
   replacements.
5. `insert_resolved_hint`, `bpfopt/crates/bpfopt/src/passes/map_inline.rs:939-1011`
   (73 LOC): validates one hint against map mutability/key size, resolves
   map-in-map inner IDs or hard-hint values, and inserts the final resolved hint.

Only `run_map_inline_round` still feels bulky. It is an orchestration function,
not a hidden framework abstraction, so I would not block convergence on its size.
