## 1. Findings

### P0 - Correctness / Fail-Fast

1. `skb_load_bytes` leaks simulated register state across non-linear BBProgram block boundaries.
   - Evidence: `scan_sites()` initializes `regs` once at `bpfopt/crates/bpfopt/src/passes/skb_load_bytes.rs:122`, then iterates physical blocks at `skb_load_bytes.rs:124-125`. It resets only when the current absolute PC is in `branch_targets` at `skb_load_bytes.rs:128-130`.
   - Why this is wrong: `branch_target_pcs()` includes taken jump/call callee targets but not every non-linear entry, notably `Terminator::Call.return_to` and ordinary block starts after non-fallthrough control flow (`bpfopt/crates/bpfopt/src/analysis/bbprogram.rs:384-398`). A helper after a BPF-to-BPF call can therefore inherit stale `r1..r4` facts from before the call, even though caller-saved registers are no longer valid for this local forward simulation.
   - Supporting contrast: `bulk_memory` already has the right block-boundary shape check in `should_reset_reg_state_at_block()` at `bpfopt/crates/bpfopt/src/passes/bulk_memory.rs:380-399`.
   - Impact: false-positive `bpf_skb_load_bytes()` specialization is possible in non-linear CFGs. This is a real pass-correctness issue, not just helper cleanup.

2. `wide_mem` silences BBProgram slot/range errors and reports them as a benign skip.
   - Evidence: `view.range_for_slots(start_slot, site.old_len)` errors are caught as `Err(_)` and converted to `SkipReason { reason: "interior branch target" }` at `bpfopt/crates/bpfopt/src/passes/wide_mem.rs:520-527`.
   - Why this violates fail-fast: `range_for_slots()` can fail for invariant problems such as zero length, slot overflow, or missing logical slot metadata, not just a recoverable branch-target case (`bpfopt/crates/bpfopt/src/analysis/bbprogram.rs:55-80`). The explicit branch-target check already exists separately at `wide_mem.rs:531-540`.
   - Related silent continues: the same pass also continues on an impossible in-range `view.insns.get(pc)` miss at `wide_mem.rs:546-549`, and on a missing current-PC map entry at `wide_mem.rs:651-660`.
   - Impact: malformed BBProgram/view state can be hidden as a clean pass result.

### P1 - Design Contract

1. `ccmp` still carries local BlockId remapping logic around BBProgram mutations.
   - Evidence: `ccmp_chain_blocks()` calls `split_block()` and then remaps `chain`, `target`, and `success` using local arithmetic at `bpfopt/crates/bpfopt/src/passes/ccmp.rs:319-325`; `apply_ccmp_site()` calls `merge_linear_chain()` and remaps `target`/`success` locally at `ccmp.rs:279-281`; the helpers are `remap_after_insert()` / `remap_after_remove()` at `ccmp.rs:379-394`.
   - Why this is non-design-conforming: pass code is depending on dense `BlockId.0` insertion/removal behavior instead of letting BBProgram mutation APIs own identity remapping. It is not flat bytecode lowering, but it is a local address-plan compatibility layer in block-ID form.
   - Impact: brittle if BBProgram block storage or mutation semantics change; also duplicates mutation knowledge that belongs in the analysis API.

### P2 - Cleanup / Fail-Fast Polish

1. `cond_select` has a production panic-family path.
   - Evidence: `materialize_value()` uses `unreachable!()` for `CondSelectValue::Reg(_)` at `bpfopt/crates/bpfopt/src/passes/cond_select.rs:672`.
   - Context: the branch is currently guarded by an early return for `Reg` at `cond_select.rs:660-662`, so this is not an observed runtime bug. It is still production panic-family code in a pass and should be rewritten as an exhaustive non-panicking match.

2. `wide_mem` treats missing verifier oracle state as safe for BTF-struct pointer widening.
   - Evidence: `run_on_bbprogram()` uses `prog.oracle.as_deref().unwrap_or(&[])` at `bpfopt/crates/bpfopt/src/passes/wide_mem.rs:507`; `base_reg_is_btf_ptr_from_states()` returns `false` when verifier states are empty at `wide_mem.rs:382-388`, and its comment explicitly lists absent offline state as safe at `wide_mem.rs:378-381`.
   - Judgment: if oracle state is optional by policy for `wide_mem`, this is an accepted structural-pass fallback and should be documented as such. If the BTF field-boundary guard is mandatory for safety, this should fail closed or skip with an explicit reason instead of fail open.

3. Kinsn proof decoders remain visibly duplicated.
   - In scope: `cond_select` wraps `decode_packed_kinsn_payload(...).and_then(...)` and validates nibble registers at `bpfopt/crates/bpfopt/src/passes/cond_select.rs:16-31`; `ccmp` repeats the same pattern with reserved-bit/register validation at `ccmp.rs:20-60`.
   - Cross-pass evidence: same local proof/uses pattern exists in `rotate.rs:24-63`, `extract.rs:17-32`, `endian.rs:53-66`, `prefetch.rs:30-46`, and `bulk_memory.rs:34-117`.
   - Impact: not a correctness blocker today, but each pass reimplements packed proof length, reserved-bit checks, and implicit register-use decoding. A small packed-payload descriptor helper would reduce future drift.

### P3 - Small Polish

1. `ccmp` has meaningless wrapper code in replacement application.
   - Evidence: `let mut replacement = ...;` followed by `replacement.split_off(0)` at `bpfopt/crates/bpfopt/src/passes/ccmp.rs:283-288`. `split_off(0)` is equivalent to moving the whole vector and only exists to satisfy the current call shape.

2. `ccmp` has an impossible validation branch.
   - Evidence: `let mode = BpfInsn::unpack_u4(payload, 6) & 0x1;` followed by `if mode > 1` at `bpfopt/crates/bpfopt/src/passes/ccmp.rs:28-40`. The mask makes the check unreachable as written.

3. Multi-block matcher helpers are still pass-local.
   - Evidence: `cond_select` has `common_successor()` at `cond_select.rs:290-296`, `single_body_insn()` at `cond_select.rs:458-460`, and `single_successor()` at `cond_select.rs:462-469`. `ccmp` has `BranchTerm` and branch-chain extraction at `ccmp.rs:145-154` and `ccmp.rs:495-548`.
   - Judgment: these are not currently duplicate enough to block, but a BBProgram helper for "conditional terminator with current PC and block-start PCs" would simplify both files.
