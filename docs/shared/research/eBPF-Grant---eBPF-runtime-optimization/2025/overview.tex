Unfortunately, LLM serving systems face correctness and performance reliability issues due to software bugs, environmental problems such as misconfiguration or model versioning mismatches, or even adversarial user input crafted to induce failures~\cite{underwood_2022_mlservingfailures}.  Due to the complexity of LLM serving systems, there is often a long causal change between a failure symptom (\eg degraded LLM performance) and its root cause (\eg a software bug).  For example, a CUDA memory allocation may lead to a hardware exception by passing through the Python-based scheduler of the serving framework, the C++ backend, and by triggering an invalid operation in the CUDA driver before it finally causes the exception.  Traditional debugging tools operate within a single framework (\eg a Pytorch profiler~\cite{pytorchprofiler} or NVIDIA GPU profiler~\cite{nsightsystems}) and provide little insight into the cause-and-effect chain that connects an LLM serving system failure (\eg the hardware exception) back to the cause (\eg the failed memory allocation).  We have performed an initial analysis of bugs in vLLM~\cite{kwon2023pagedattention}, an open-source LLM serving system, and shown that this complexity balloons debugging time: the average bug reported against vLLM takes 115 days before being marked as closed or solved.

We propose work that will create new techniques and tools that enable LLM serving observability.  The proposed work models a multi-layer heterogeneous LLM serving system as a distribute system and adopts  distributed tracing to support its observability.  The work will use the eBPF design methodology---static verification and lightweight instrumentation---to provide safe and efficient observability to each system layer in an LLM serving system, similar to the PI's prior work on using eBPF design to add safe and efficient observability to userspace applications~\cite{zheng2025extending}.  If successful, the proposed work will (1) establish techniques that enable debugging, configuration management, and security forensics for LLM serving systems and (2) create infrastructure that realizes these techniques to improve the reliability of LLM serving systems. 

\noindent \textbf{Related Work.} 
Many tools support observing the behavior of a single software layer including CPU profilers; GPU profilers such as Nvidia Nsight~\cite{nsightsystems} and AMD rocTracer\cite{rocmtracer}; application-level LLM platforms such as Langfuse~\cite{langfuse2025} and Datadog~\cite{datadog2025}; and dynamic instrumentation tools for CPUs, such as Intel PIN~\cite{Luk_2005_pin}, and GPUs, such as Nvidia NVBit~\cite{Villa_2019_NVBit} and Intel GTPin~\cite{Skaletsky_2022_gtpin}. The PI and her graduate student are uniquely skill for the proposed research due to their expertise in extending eBPF to new domains~\cite{zheng2025extending}, tracing low-level software behavior~\cite{Quinn_2018_sledgehammer}, and building novel debugging tools for software~\cite{Quinn_2022_omnitable} and heterogeneous systems~\cite{Ma_2022_bnw}.

\noindent \textbf{Research Plan.}  We will construct a system that enables LLM serving system observability safely and efficiently by extending the eBPF workflow to support cross-layer and cross-architecture scenarios.  Our proposal suggests that we model heterogeneous, multi-layer systems as distributed systems and apply ideas from distributed tracing (\eg X-Trace~\cite{fonseca2007xtrace} and Dapper~\cite{sigelman2010dapper}) to support observability; this insight is related to the idea of modeling a multicore system as a distributed system as done in the Multikernel~\cite{Baumann_2009_multikernel}.  The work will first study bugs in open-source LLM serving systems to craft benchmarks, understand current developer debugging challenges, and identify the specific low-level events that are necessary for comprehensive observability.  Then, we will design an interface and establish design principles for creating runtimes that emit observability  output from a system layer; the principles will illustrate how developers can use eBPF-style verification and instrumentation to add safe and efficient observability support to a system layer.  We will follow the design principles to create observability runtimes for GPUs, NPUs, and the vLLM control-plane.  Finally, we will design a data model and high-level declarative interface that allow users to analyze observability data after the fact or through runtime monitors; we will create a prototype implementation of the model that we will evaluate on the benchmarks crafted from the bug study.

\textbf{Introduction.} Many modern applications have large code footprints on the order of tens to hundreds of MBs~\cite{ayers2019asmdb,panchenko2019bolt,Ottoni:2017:OFP:3049832.3049858}). Unfortunately, instruction caches of modern processors are comparatively small (less than 1 MB). Consequently, modern applications suffer from frequent stalls due to poor instruction locality~\cite{ayers2019asmdb}. To improve instruction locality, these applications are optimized via profile-guided optimizations (PGO) (e.g., Facebook Bolt~\cite{panchenko2019bolt}, Google AutoFDO~\cite{chen2016autofdo}). Traditionally, PGOs work by first instrumenting an application, then gathering a representative profile of the dynamic control flow, and finally rebuilding the application to modify the code layout based on the collected profile. 

Although PGOs provide significant speedup (up to 30\%~\cite{chen2016autofdo}), the instrumented execution incurs high overhead (up to $10\times$~\cite{Chen:2010:THE:1772954.1772963}). To avoid such overheads, recent works rely on sampling hardware performance events~\cite{chen2016autofdo,panchenko2019bolt}. Modern processors have performance monitoring units that can collect samples of control flow information (e.g., last branch record, Intel PT, ARM ETM, etc.) with low overhead (i.e, less than 1\%). State-of-the-art performance monitoring and optimization tools (Facebook BOLT~\cite{panchenko2019bolt}, Google AutoFDO~\cite{chen2016autofdo}) use performance monitoring units to collect in-production execution profiles for data-center applications and apply PGOs accordingly. Not only these tools provide performance gains comparable to traditional instrumentation-based PGOs, they are used in production systems due to their low-overhead and ease of deployment.

While PGOs that rely on hardware sampling have been effective for datacenter applications, significant challenges impede their adoption in mobile systems, which also suffer from large code footprints~\cite{ren2019improving}. However, user-mode mobile applications do not have access permissions to the performance monitoring units of mobile processors. This is in contrast to a setting where developers have control over the machines (e.g., in a datacenter). Therefore, mobile application developers cannot gather samples of hardware events from in-production executions, and instead rely on software instrumentation for profiling~\cite{ren2019improving}. While instrumentation-based PGOs provide significant performance improvements for mobile applications, the instrumentation incurs high runtime overhead. Consequently, instrumented mobile applications are used only for dogfooding (e.g., as in the deployment of the Facebook iOS App~\cite{ren2019improving}) and are not deployed in production.

\noindent \textbf{Proposed Research.} Our goal is to enable PGOs for mobile applications using profiles gathered in production. Our key idea is to build a distributed performance tracing system that will split the overhead of profiling among multiple mobile devices. If successful, we will develop novel techniques for distributed performance tracing and  enable comprehensive PGOs for mobile devices.

We will systematically instrument different parts of a system, aggregate profiling data, and perform PGOs. \textit{Our primary focus is efficient instrumentation and performance tracing}; we will rely on the plethora of existing PGOs to optimize programs once the profile is collected. For platforms like Android, we will leverage existing dynamic binary rewriting facilities~\cite{ghuloum2014art} to selectively instrument the applications. However, this approach is not always feasible. For instance, the iOS platform does not allow dynamically altering an application's binary~\cite{lian2015too}. To address this challenge, we will rely on the inherent variability that stems from different mobile devices, operating systems, and application versions. For instance, popular applications like Facebook and Instagram are updated quite often and at any given time, multiple versions of the same application is deployed in production~\cite{rossi2016continuous}. Our techniques will use this variability to deploy different versions of an application with different instrumentation. To determine how the instrumentation should be distributed 
(via dynamic binary rewriting or by relying on the diversity of application/OS/device versions), we will use a hierarchical instrumentation approach that is also cognizant of different phases of an application.

\textit{Hierarchical instrumentation} splits the instrumentation overhead by leveraging the hierarchical structure of a program's control flow graph (CFG). Consider the CFG in Fig.~\ref{fig:hierarchical}. Basic blocks $B_3$ and $B_4$ in Fig.~\ref{fig:hierarchical} can only be executed if control flow transitions from basic block $B_0$ to $B_1$. Similarly, executions of $B_5$ and $B_6$ are dependent on a transition from $B_0$ to $B_2$. Therefore, our proposed approach will first add instrumentation to track the control transfer edges originating at $B_0$ (to $B_1$ and $B_2$). If profiles indicate that a particular transition is more frequent (i.e., a potential bottleneck), hierarchical instrumentation will instrument the control flow edges to track the lower levels of the CFG hierarchy accordingly. For instance, if the $B_0$ to $B_1$ transition is more frequent, our approach will subsequently monitor the edges $B_1$ to $B_3$ and $B_1$ to $B_4$.

\textit{Phase-based instrumentation} makes the observation that applications go through different phases during their lifetimes. Oftentimes, these phases are executed by different components (e.g., classes, functions, etc.). For example, certain components of applications are primarily used during the startup phase while other components are used during inactive phases while the application is running in the background. Our approach will map phases to the control flow graph of an application and distribute instrumentation to different phases to reduce the overhead of performance tracing. For instance, Android and iOS applications register these components via different callbacks. We will identify different components by investigating the call graph initiated by these callbacks. Consider the CFG in Fig.~\ref{fig:selective}. If we can identify that basic blocks $B_0$-$B_3$ are mostly relevant for phase 1 and basic blocks $B_4$-$B_6$ are relevant for phase 2, then we can employ phase-based selective instrumentation. Moreover, if a given phase (e.g., startup phase) is more important than other phases in terms of instruction locality, we can add more instrumentation to control flow components corresponding to that phase, an approach taken by a recent Facebook project~\cite{ren2019improving}.

Our proposed distributed instrumentation approach is inspired by two key observations. First, all control flow changes are not equally important regarding program’s instruction locality. \textbf{Further Challenges and Mitigation Strategies.} Combining profiles across multiple executions from different end devices running different versions of an application can be a significant challenge. In many cases, the profiling information can depend heavily on the execution context (e.g., the callsites, inputs) and application versions. To overcome this challenge, we will extract from each profile a subset of the data that pertains to the version of the software that we try to optimize. Moreover, we can apply statistical comparison techniques to find correlations between performance traces and application version changes~\cite{kaldor2017canopy}.

%outcome of a control flow instruction depends on the current context in the form of outcomes of last few control flow instructions. If we distribute instrumentations naively across different control flow instructions, the collected profile may lose this correlation. To avoid losing such correlations, our proposed mechanism will distribute instrumentation in a way that highly correlated control flows are instrumented in same execution. Our technique will determine the correlation among different control flows based on static analysis as well as dogfooded executions.
