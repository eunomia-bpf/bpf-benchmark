## 1. Opaque pass-through schema integrity

Verdict: CORRECT post-`45c7a647`; WRONG in `c510c646`, fixed by `45c7a647`.

Current daemon shape is opaque. `PassDetail` stores `bpfopt_summary` as a `serde_json::Value` (`daemon/src/commands.rs:174-180`). `run_bpfopt_pass()` returns `Result<Value>` and reads the report as one JSON value (`daemon/src/commands.rs:614-625`, `daemon/src/commands.rs:641-645`). The generic JSON reader only parses the file into the requested type (`daemon/src/commands.rs:978-980`). `pass_detail()` stores the optional `Value` directly or `null` (`daemon/src/commands.rs:656-667`). I found no current daemon `bpfopt_summary.get(...)`, `Value::as_*()`, or equivalent field-level read of the opaque blob.

`c510c646` still violated the opaque boundary. It added top-level `OptimizeOneResult.inlined_map_entries` (`c510c646:daemon/src/commands.rs:128-135`) and a daemon-local `InlinedMapEntry` type (`c510c646:daemon/src/commands.rs:158-163`). Its `collect_inlined_map_entries()` parsed `pass.bpfopt_summary.get("map_inline_records")` (`c510c646:daemon/src/commands.rs:298-305`), required `as_array()` (`c510c646:daemon/src/commands.rs:307-309`), and read `map_id`, `key_hex`, and `value_hex` field-by-field (`c510c646:daemon/src/commands.rs:311-322`).

Concrete trigger in `c510c646`: any successful `map_inline` pass whose bpfopt report omitted or malformed `map_inline_records` would make the daemon interpret the opaque report and potentially fail the program after the pass chain (`c510c646:daemon/src/commands.rs:630-646`). Origin: `c510c646`; fixed by `45c7a647`, which removed `collect_inlined_map_entries()` and the top-level daemon field.

## 2. Daemon to runner Python schema match

Verdict: CORRECT post-`45c7a647`.

The daemon emits one per-program `OptimizeOneResult` with `status`, `prog_id`, `program`, `passes`, and optional `error_message`; there is no current daemon top-level `inlined_map_entries` field (`daemon/src/commands.rs:128-135`). Each pass record has `pass`, `status`, `error`, and `bpfopt_summary` (`daemon/src/commands.rs:174-180`). The server wraps those program records in `per_program` plus top-level `status` and `error_message` (`daemon/src/server.rs:206-227`).

Runner Python accepts this shape without typed pass deserialization. `_apply_result_from_response()` shallow-copies the daemon per-program object and derives only `error` from `error_message` (`runner/libs/rejit.py:225-230`). `apply_daemon_rejit()` validates only that `per_program` is an object and matches requested program IDs before forwarding each record (`runner/libs/rejit.py:366-386`). `corpus/driver.py` stores the forwarded `rejit_result` dict in app results (`corpus/driver.py:391-394`, `corpus/driver.py:368-377`), and artifact writing serializes the result payload as `details/result.json` (`runner/libs/run_artifacts.py:55-77`).

The `inlined_map_entries` data moved into bpfopt's pass report, not into Python normalization. Current bpfopt report includes `inlined_map_entries` on `PassReport` (`bpfopt/crates/bpfopt/src/main.rs:155-168`) and serializes `map_id`, `key_hex`, and `value_hex` from `MapInlineRecord` (`bpfopt/crates/bpfopt/src/main.rs:1170-1183`). The CLI pipeline test asserts the current report field and value hex (`bpfopt/crates/bpfopt/tests/cli_pipeline.rs:391-395`). Python does not read either old top-level `inlined_map_entries` or nested `passes[*].bpfopt_summary.inlined_map_entries`; it preserves the daemon record.

Concrete trigger checked: a current daemon record with `passes[*].bpfopt_summary.inlined_map_entries` and no top-level `inlined_map_entries` is accepted because runner code copies the record rather than requiring the old field (`runner/libs/rejit.py:225-230`, `runner/libs/rejit.py:380-386`). Origin: no current bug; `45c7a647` fixed the `c510c646` daemon-side top-level field.

## 4. Cascade semantics

Verdict: CORRECT post-`45c7a647`.

`run_pass_chain()` iterates the full pass list and pushes exactly one returned `PassDetail` per pass (`daemon/src/commands.rs:603-611`). `try_apply_one()` returns a `PassDetail` instead of aborting for missing verifier states (`daemon/src/commands.rs:471-480`), bpfopt invocation failure (`daemon/src/commands.rs:494-514`), missing pass output (`daemon/src/commands.rs:516-525`), invalid pass bytecode (`daemon/src/commands.rs:527-538`), and ReJIT failure (`daemon/src/commands.rs:539-549`). Success writes verifier states, marks them ready, updates `current_bytes`, and returns `Ok` for that pass (`daemon/src/commands.rs:551-555`).

An earlier failed ReJIT does not silently prevent later passes. The dependent pass is attempted by the loop and recorded as `skipped_missing_states` when `verifier_states_ready` is still false (`daemon/src/commands.rs:471-480`). The c510 smoke artifact demonstrates this visible cascade shape for prog 11: `noop` records `failed_rejit` and the following `map_inline` records `skipped_missing_states` (`corpus/results/x86_kvm_corpus_20260505_173242_158725/details/result.json:632-656`).

Concrete trigger checked: `enabled_passes=["noop","map_inline"]` where `noop` fails `BPF_PROG_REJIT`. Current expected output is two pass details, not an aborted chain. Origin: no current bug.
