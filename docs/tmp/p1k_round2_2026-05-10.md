# P1-K const_prop round 2

Date: 2026-05-10

## Root cause

`const_prop` could still materialize pointer arithmetic when local bytecode pointer provenance was known only by instruction semantics, not by the verifier oracle at the same raw PC.

The bad workdir site is raw input PC 5162 in `/tmp/p1k_workdir/output_step6.bin`:

```text
5161: r1 = r10
5162: r1 += -64
5163: r2 = 16
5164: call 112
```

Round 1 let this become, after one earlier const_prop insertion shifted the visible rejection PC by +1:

```text
5162: r1 = r10
5163: r1 = 8
5164: r2 = 16
5165: call 112
```

The prior verifier log has the real pointer post-state, but at verifier PC 5172:

```text
/tmp/p1k_workdir/verifier_log_step6.log:13901:5171: (bf) r1 = r10 ; R1=fp0 R10=fp0
/tmp/p1k_workdir/verifier_log_step6.log:13902:5172: (07) r1 += -64 ; R1=fp-64
```

At raw PC 5162, the verifier log contains an unrelated scalar post-state:

```text
/tmp/p1k_workdir/verifier_log_step6.log:13892:5162: (73) *(u8 *)(r2 +736) = r1 ; R1=8 ...
```

So the round-1 decision path was:

- `instruction_post_state_has_pointer_type_in_context(5162, None, 1)` returned false because the +8 window ended at 5170.
- `instruction_post_state_proves_scalar_exact_in_context(5162, None, 1, 8, Bits64)` returned true from the unrelated `R1=8` state at PC 5162.
- `fold_alu_instruction` emitted `r1 = 8`.

## Hypotheses

- (a) Refuted. The prior log does print the pointer post-state: `R1=fp-64` at PC 5172.
- (b) Refuted. The parser classifies `fp...` as reg_type `fp` in `bpfopt/crates/bpfopt/src/verifier_log.rs:535`.
- (c) Confirmed for this workdir. The raw bytecode scan PC is 5162; the matching verifier pointer state is PC 5172.
- (d) Partially confirmed, but not fixed by broadening. The +8 pointer lookahead was too small for this drift, but widening it would still be heuristic. The fix is to preserve local pointer provenance and fail closed before consulting shifted verifier scalar facts.

## Fix

`bpfopt/crates/bpfopt/src/passes/const_prop.rs` now carries `may_pointer` in `RegConstFact`.

- R10 starts as a pointer in `unknown_state`.
- Pointer facts propagate through register MOV and ALU inputs.
- Oracle scalar facts do not overwrite a local may-pointer fact.
- `fold_alu_instruction` skips materialization when either ALU input may be a pointer, before using verifier scalar post-state proof.

Key code:

- `RegConstFact::may_pointer`: `const_prop.rs:22`
- ALU pointer propagation: `const_prop.rs:590`
- pre-materialization pointer skip: `const_prop.rs:650`
- oracle facts preserve local pointer facts: `const_prop.rs:821`
- R10 pointer initialization: `const_prop.rs:872`
