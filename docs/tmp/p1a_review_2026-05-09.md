## API Design Review

`RewritePlan` additions are reasonable and remain small:

- `replace_range(...) -> anyhow::Result<()>` and `delete_range(...) -> anyhow::Result<()>` now report duplicate/overflow planning failures instead of panicking. All current call sites found by `rg "replace_range\\(|delete_range\\("` propagate with `?`.
- `BtfRemapPolicy::RemapKinsn(&KinsnRegistry)` matches the old kinsn-pass behavior: after mutation, it calls `remap_kinsn_btf_metadata(program, registry)` and then always calls `program.remap_annotations(&addr_map)`.
- `insert_before(pc, insns)` is used by `prefetch`; `add_internal_branch(...)` is used by `ccmp`. No dead fields or `#[allow(dead_code)]` were introduced.
- Mixed commit ordering is correct for the current users: at each old PC, `commit` records `addr_map[pc]`, emits insertions, then applies replacement/delete/copy. It then applies old-branch fixup and finally patches synthetic internal branches.
- `insert_before` keeps the old prefetch semantics: a branch to old `insert_pc` lands before the inserted prefetch sequence, because `addr_map[insert_pc]` is captured before insertion.
- `add_internal_branch` patching computes `target_new_pc - (branch_new_pc + 1)`, the same formula as old `fixup_ccmp_branches`.

### endian_fusion

The old implementation emitted `call`, copied the middle instructions `old_start+1 .. old_end-1`, deleted the terminal endian instruction, and used `map_endian_replacement` to map:

- load PC -> first replacement instruction
- middle old PCs -> copied middle instructions after the call
- terminal endian PC -> end of the replacement stream

The new model at `endian.rs:483` is equivalent:

- `replace_range(site.start_pc, 1, emit_endian_fusion_call(...))` maps the load PC to the call sequence.
- The normal `RewritePlan` copy path preserves middle instructions in original order.
- `delete_range(site.start_pc + site.old_len - 1, 1)` maps the terminal endian instruction to the current output length after middle instructions have been copied.

For the common 2-insn case, the terminal maps just after the call. For narrowed sites with intervening instructions, the intervening instructions survive between the call and the terminal mapping, matching the deleted `map_endian_replacement` logic. Branch fixup still uses the shared helper. BTF remap is equivalent through `RemapKinsn`; annotations use the new `addr_map`.

Coverage includes branch-over-site fixup and interior-target skip tests, but there is no dedicated regression test that asserts the narrowed-site middle-instruction mapping. That is a coverage gap, not an observed bug.

### ccmp

`scan_ccmp_sites` still walks ascending chains and skips by `old_len`. The migrated replacement at `ccmp.rs:217` emits the same packed ccmp sidecar+call and then appends the same `JEQ dst_reg, 0, off=0` placeholder. `branch_idx = replacement.len()` is the same location as old `branch_pc = new_insns.len()` after emitting the packed call.

`add_internal_branch(site.start_pc, branch_idx, site.target_pc)` gives `RewritePlan` the same old target PC that `PendingCcmpBranch.old_target_pc` used. `patch_internal_branches` computes the same relative offset and writes it to the JEQ `off`. The existing `ccmp_pass_emits_kinsn_and_final_branch_on_aarch64` test checks the resulting JEQ offset in the simple growth case.

BTF and annotation remap are equivalent to the old pass.

### bulk_memory

The scan path and safety checks are unchanged. `safe_sites` remains ascending and non-overlapping because `scan_sites` advances by each accepted site's `old_len`. The migrated path at `bulk_memory.rs:210` calls the existing `emit_site_replacement` helper with the same BTF IDs and static call offsets. Payload chunk order for memcpy/memset is unchanged because `emit_site_replacement` was not changed.

Branch fixup, kinsn BTF remap, and annotations are handled by `RewritePlan` with the same shared helpers.

### prefetch

The candidate scan, scoring, insertion-point selection, and `dedup_candidates` ordering are unchanged. Old code grouped the already-deduped candidate list by `insert_pc` in a `BTreeMap`, preserving candidate order inside each group. New code iterates the same list and calls `insert_before`; `insert_before` appends to the per-PC vector, so multiple insertions at the same PC retain the same order.

The `RewritePlan` insertion semantics match the old loop: `addr_map[pc]` points before inserted prefetch instructions, so branches to the old PC execute the inserted prefetch first and then the original target instruction. BTF remap and annotations match old behavior.

Coverage exercises map-value, alias, packet, and instruction-boundary insertion; it does not explicitly test two distinct prefetches at the same insertion PC. The implementation order is still equivalent by inspection.
