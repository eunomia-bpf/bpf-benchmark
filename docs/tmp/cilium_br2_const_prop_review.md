# Cilium BR2 const_prop adversarial review

## A. Evidence integrity

Verdict: conclusion 1 is directionally strong, but the exact wording should be "the minimal `noop,const_prop` verifier-state pipeline breaks Cilium", not "bare `const_prop` alone"; `const_prop` requires `--verifier-states`, and the registry marks it as both needing and producing verifier states (`bpfopt/crates/bpfopt/src/passes/mod.rs:130`, `bpfopt/crates/bpfopt/src/passes/mod.rs:132`, `bpfopt/crates/bpfopt/src/main.rs:355`). Evidence is good: `noop,wide_mem` completed with post-ReJIT workload present (`corpus/results/x86_kvm_corpus_20260508_190434_103001/metadata.json:3`, `corpus/results/x86_kvm_corpus_20260508_190434_103001/details/apps/cilium__agent.json:848`), `noop,wide_mem,const_prop,dce` timed out before recording post-ReJIT payload (`corpus/results/x86_kvm_corpus_20260508_190947_955043/metadata.json:2`, `corpus/results/x86_kvm_corpus_20260508_190947_955043/details/apps/cilium__agent.json:767`), and `noop,const_prop` reproduced the same 31 s host-to-endpoint timeout (`corpus/results/x86_kvm_corpus_20260508_191351_975279/metadata.json:2`, `corpus/results/x86_kvm_corpus_20260508_191351_975279/details/apps/cilium__agent.json:830`). Step 4 is now complete and materially reduces the DCE objection: `noop,dce` completed, with post-ReJIT workload recorded (`corpus/results/x86_kvm_corpus_20260508_193004_621409/metadata.json:3`, `corpus/results/x86_kvm_corpus_20260508_193004_621409/details/apps/cilium__agent.json:848`). The main remaining confounders are repetition and scope: all isolating runs are Cilium-only, `SAMPLES=1`, 10 s workload, and one VM target, so this is enough to isolate a correctness bug for triage but not enough to make a cross-suite reliability claim. I do not think a pure `noop` rerun is required for the blame assignment because both `noop,wide_mem` and `noop,dce` survived, and `noop` is explicitly an identity pass (`bpfopt/crates/bpfopt/src/passes/noop.rs:18`). A repeat of `noop,const_prop` with `KEEP_WORKDIRS=all` would be useful only to silence timing-objection reviewers and preserve the rewritten bytes for `cil_from_host`, `cil_from_netdev`, and `cil_to_netdev`. Verdict on conclusion 2 is also favorable: `wrk` timeout propagates through `run_command()` because `subprocess.run(..., timeout=...)` is not caught there (`runner/libs/__init__.py:117`), `_run_wrk_http_load()` does not swallow it (`runner/libs/workload.py:749`), and the lifecycle records then raises the app error (`runner/libs/case_common.py:265`, `runner/libs/case_common.py:310`). Pushback: do not call this a fully audited rollback story unless you cite the exact reverted change; the artifact and current code prove the current behavior raises and records `post_rejit: null`, not the history.

## B. const_prop root-cause candidates

### B1. Delta-state oracle is under-proved

Most likely bug: `VerifierExactConstOracle::from_states()` only consumes `InsnDeltaState` records and builds facts from registers mentioned in those delta records (`bpfopt/crates/bpfopt/src/passes/const_prop.rs:121`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:125`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:129`). The consensus logic detects conflicting observed scalar values, but it does not prove that every verifier occurrence at that PC observed the register, nor does it reconstruct a full state when a register is omitted (`bpfopt/crates/bpfopt/src/passes/const_prop.rs:77`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:107`). Cilium is a better trigger than bcc/bpftrace/katran/otel/tetragon/tracee because its host/LXC datapath is a large packet-classification graph with many map-dependent and endpoint-dependent branches, so a register can be exact on one explored edge and merely absent from another; the investigation already shows many critical tail/direct programs affected (`docs/tmp/cilium_br2_post_rejit_investigation.md:270`, `docs/tmp/cilium_br2_post_rejit_investigation.md:410`). Verify this first by instrumenting each replacement with "all verifier occurrences at pc, frame, reg" and failing closed with an explicit skip reason when any occurrence lacks a reconstructed exact value; a unit test should use a diamond CFG where one branch reports an exact delta and the join path has no mention of that register.

### B2. Path/frame-insensitive facts are applied globally

Second likely bug: the oracle key is only `(pc, reg)`, and the post-state injection applies that fact unconditionally to the abstract interpreter state after every instruction (`bpfopt/crates/bpfopt/src/passes/const_prop.rs:31`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:145`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:158`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:375`). `solve_block_entry_states()` then propagates those facts through a single CFG state per block, with predecessor meet but no edge-sensitive verifier occurrence identity (`bpfopt/crates/bpfopt/src/passes/const_prop.rs:259`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:272`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:293`). The verifier parser can preserve `frame`, `from_pc`, and speculative-edge state (`bpfopt/crates/kernel-sys/src/verifier_log.rs:88`, `bpfopt/crates/kernel-sys/src/verifier_log.rs:129`), but const_prop throws most of that away at the oracle boundary. Cilium has the right shape because direct programs such as `cil_from_host`, `cil_from_netdev`, and `cil_to_netdev` dispatch into PROG_ARRAY-heavy policy and endpoint paths (`runner/repos/cilium/bpf/lib/tailcall.h:104`, `runner/repos/cilium/bpf/lib/local_delivery.h:15`, `runner/repos/cilium/bpf/lib/local_delivery.h:32`). Verify by temporarily disabling `oracle.apply_post_state()` while leaving same-PC `exact_for_instruction()` replacements enabled; if the timeout disappears or applied-site set collapses on Cilium, the bug is propagation of path-specific facts rather than arithmetic evaluation.

### B3. Call/context handling is too coarse

Third likely bug: calls are modeled as "clear R0-R5, keep everything else" for every BPF call, and any later R0 exactness comes back only through the same context-insensitive oracle (`bpfopt/crates/bpfopt/src/passes/const_prop.rs:364`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:365`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:366`). The CFG does identify pseudo-call subprogram entries, but call edges are still treated as fallthrough for block-state propagation, so const_prop has no context-sensitive caller/callee summary (`bpfopt/crates/bpfopt/src/analysis/cfg.rs:58`, `bpfopt/crates/bpfopt/src/analysis/cfg.rs:158`). This is less proven than B1/B2 because the current report does not show replacement PCs, but Cilium's generated datapath is exactly where helper returns, tail-call fallback returns, and bpf2bpf-style helper wrappers tend to sit near branch decisions and action constants. A useful sanity check is to log every replacement whose source fact comes from the verifier oracle for R0 within a few instructions after a call, then rerun only the captured Cilium program offline if the workdir has bytecode and verifier states. For contrast, `map_inline` already treats verifier states as per-occurrence evidence and checks all occurrence-derived candidates agree (`bpfopt/crates/bpfopt/src/passes/map_inline.rs:780`, `bpfopt/crates/bpfopt/src/passes/map_inline.rs:815`, `bpfopt/crates/bpfopt/src/passes/map_inline.rs:839`); const_prop should move toward that proof style. I would deprioritize the `ldimm64` endian hypothesis for this failure because the Cilium `noop,const_prop` run reports zero instruction-count delta for all const_prop applications, so the failing replacements are same-width MOV materializations, not LD_IMM64 expansion (`docs/tmp/cilium_br2_post_rejit_investigation.md:410`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:569`, `bpfopt/crates/bpfopt/src/passes/const_prop.rs:586`).

## C. BR-5 decision

Verdict: BR-5 is a reasonable short-term measurement policy if it is named honestly and applied suite-wide, not as a per-app or per-program exclusion. The benchmark rules forbid filtering individual BPF programs or hiding ReJIT failures (`CLAUDE.md:5`), but they do allow a whole-run pass-list override via `BPFREJIT_BENCH_PASSES` (`CLAUDE.md:138`). The paper risk is real: the default benchmark config still includes `const_prop` on both x86_64 and arm64 (`corpus/config/benchmark_config.yaml:3`, `corpus/config/benchmark_config.yaml:12`, `corpus/config/benchmark_config.yaml:27`), and the plan describes verifier const propagation as an implemented bytecode rewrite (`docs/kernel-jit-optimization-plan.md:231`). Therefore the paper should not say "all bytecode-rewrite passes" without a footnote; the defensible phrasing is "BR-5 excludes verifier-state const_prop after a Cilium semantic regression, pending fix." The other risk is performance attribution: DCE is documented as benefiting from const_prop/map_inline (`docs/kernel-jit-optimization-plan.md:232`), so removing const_prop may reduce DCE's exposed opportunities and may change other apps' apparent improvement, even if it improves correctness. Step 4 shows DCE alone is not the Cilium data-path killer, but it does not prove BR-5 will preserve BR2's non-Cilium gains (`corpus/results/x86_kvm_corpus_20260508_193004_621409/details/apps/cilium__agent.json:848`). Keep `noop` in BR-5 only if the intended policy includes verifier-state producer overhead and matches the existing BR2 sequencing; otherwise it is not an optimization pass, just an identity ReJIT round trip (`bpfopt/crates/bpfopt/src/passes/noop.rs:4`). The final authoritative run should report the exact pass list, not imply it is the default config.

## D. Fix path

A serious fix is medium-sized: 1-2 days to localize replacement PCs and 3-5 days to rewrite the oracle proof model, plus Cilium and 7-app reruns. Do not start in the kernel or runner; the kernel verifier accepted the transformed bytecode, so this is a userspace semantic-preservation bug in const_prop. First capture successful const_prop workdirs for Cilium with bytecode, verifier states, and pass reports, because the current success artifacts only preserve the failed `dump_bpf_prog` workdir and not the rewritten critical datapath programs (`corpus/results/x86_kvm_corpus_20260508_191351_975279/details/failure-artifacts/11.tar.gz`, `runner/libs/rejit.py:379`). Second, add diagnostics that classify each replacement as local-eval-derived or oracle-derived, with PC, dst reg, ALU width, source verifier occurrence count, frame count, and whether any occurrence was missing. Third, implement a fail-closed oracle: a replacement is legal only when every relevant verifier occurrence at `(pc, frame, from_pc)` reconstructs the same exact post-value, otherwise record a skip reason rather than silently materializing a constant. Fourth, add regression tests with bug-detection value: one diamond-path missing-observation test, one multi-frame or repeated-subprog-call test, and one post-call R0 exactness test; these directly target the classes above and fit the unit-test quality rule (`CLAUDE.md:79`). Fifth, only after unit tests pass, run the narrow Cilium `noop,const_prop` reproduction, then BR2 Cilium, then the 7-app authoritative target. I would rewrite the oracle before trying scattered guards, because the current design makes it too easy to add one-off exceptions while keeping the core proof obligation unsound. Runtime sanity assertions are still useful during triage, but production behavior should be explicit skip reasons in the pass report, not panic-on-valid-program and not hidden fallback. The expected review artifact after the fix is a before/after table of replacement PCs in Cilium critical programs, not just "wrk passed", because app success alone will not prove the oracle is sound.
