# V4b matcher 统一 review

## 1. 正确性 verdict

PASS.

我没有发现 matcher 统一引入的功能丢失或语义破坏。

- `bpfopt/crates/bpfopt/src/pass.rs:812` 的 `apply_candidates_reverse` 保留了原先的 reverse-apply 语义: 候选按原程序顺序收集, 应用时反向遍历, 每个候选由 callback 返回 `(old_len, replacement)` 后走 `try_replace_range_with_skips`。`endian` 在 `bpfopt/crates/bpfopt/src/passes/endian.rs:302` 需要 `start` 来计算 `preserved_body_insns`, 新 callback 形态覆盖了这个需求。
- `bpfopt/crates/bpfopt/src/pass.rs:844` 的 `check_cross_block_pair_pattern` 对 `extract`/`endian` 的 2-insn 邻接 matcher 等价: 只在 `start` 是当前 block 最后一个 body site、terminator 是唯一 fallthrough successor、next block 首 site 与 pair matcher 命中时记录 skip。`extract.rs:66` 和 `endian.rs:272` 的调用都只依赖这个 2-insn pair 语义。
- `rotate` 的 tmp_reg 检查从 apply closure 前移到候选预过滤, 见 `bpfopt/crates/bpfopt/src/passes/rotate.rs:85`。我没有找到具体反例。后续 reverse apply 的 later candidate 若把自己的 tmp use 删除, 该 tmp 在 later window 内先被定义, 不会让 earlier window 的同名寄存器 live-out 变真；若 later candidate 的 `val_reg` 是 earlier tmp, replacement 仍使用该寄存器, pre-loop 与 closure 内检查一致。
- `PassResult::with_sites` 在 `bpfopt/crates/bpfopt/src/pass.rs:439` 用 `..Default::default()`。对当前字段而言与 `..PassResult::unchanged()` 的语义对齐: `sites_applied=0`, 空 diagnostics/site diagnostics/map records, `insns_before/after=0`, test-only `sites_skipped=[]`。保留 struct literal 的 `const_prop`/`map_inline` 调用点都有额外 diagnostics 或 map records, 不应机械替换。
- `as_kernel` / `alu32_reg` 只在测试路径命中: `bpfopt/crates/bpfopt/src/insn.rs:257`, `bpfopt/crates/bpfopt/src/insn.rs:558`; 调用分别在 `insn.rs` 内部 test 和 `passes/rotate_tests.rs:61`。

## 3. 跨 pass dedup 提议

1. 统一条件跳转反转:

```rust
pub(crate) fn invert_cond_jmp_op(op: u8) -> Option<u8>
```

替换 `bpfopt/crates/bpfopt/src/passes/cond_select.rs:552` 的 `inverse_jcc_op` 和 `bpfopt/crates/bpfopt/src/passes/branch_flip.rs:493` 的 `invert_jcc_op`。这两个表基本同构, 唯一区别是命名。

2. 统一 checked skip-site helper:

```rust
pub(crate) fn checked_site_skip(
    prog: &BBProgram,
    site: InsnSite,
    reason: impl Into<String>,
) -> anyhow::Result<SiteSkipReason>
```

替换 `prefetch.rs:365` 的 `pf_skip_reason` 和 `branch_flip.rs:186` 的 `bf_skip_reason`。两者都是 `prog.insn(site)?` 后构造 `SiteSkipReason::new`。

3. 统一 reverse body deletion:

```rust
pub(crate) fn delete_body_sites_reverse<I>(
    prog: &mut BBProgram,
    sites: I,
    skipped: &mut Vec<SiteSkipReason>,
) -> anyhow::Result<usize>
where
    I: IntoIterator<Item = InsnSite>;
```

可吃掉 `bounds_check_merge.rs:147` 的 `deletions_by_block`/reverse sort/delete body sites 模式, 也能给 `map_inline.rs:1635` 的 body-site 删除分支复用。terminator 删除仍留在 pass-local, 因为 map_inline 和 bounds_check_merge 的 terminator 语义不同。

4. 统一 frame-site scanning:

```rust
pub(crate) fn sites_after_in_frame(
    prog: &BBProgram,
    start: InsnSite,
) -> anyhow::Result<Vec<InsnSite>>;

pub(crate) fn sites_before_in_frame_rev(
    prog: &BBProgram,
    end: InsnSite,
) -> anyhow::Result<Vec<InsnSite>>;
```

`map_inline.rs:203`/`222` 已有 pass-local 实现; `prefetch.rs:386` 的 `pf_sites_after_in_frame` 是 layout-window 变体。可以先把无 window 版本下沉到 `BBProgram`, 再让 prefetch 的 window helper 复用 frame iteration。

5. 统一 alias/write predicates 中的小块:

```rust
pub(crate) fn mem_base_reg(insn: &BpfInsn) -> Option<u8>;
pub(crate) fn writes_scalar_reg(insn: &BpfInsn, reg: u8) -> bool;
```

`prefetch.rs:331` 有 `memory_base_reg`; `endian.rs:177` 和 `prefetch.rs:508` 有相近但不完全一致的 `writes_reg`。先抽出保守 common predicate, pass-specific 特例留在 caller。

## 5. 总评估

现实可砍: 约 350-500 LOC。

最稳的顺序:

1. 先做 `map_inline.rs` 单 caller / 占位路径清理, 目标约 180-260 LOC。这里收益最大, 但不要碰核心 lookup/classify 语义。
2. 再做 `bbprogram.rs`/`bbprogram_api.rs` dead API 和 test-only wrapper 清理, 目标约 80-130 LOC。
3. 再做 `insn.rs` public surface 收窄: 生产 0 caller 的 constructor 先 `cfg(test)` 或迁到 test helper, 单 caller public helper 改 private/inline。LOC 收益不大, 但符合 fail-fast/no public unused API。
4. 最后做跨 pass dedup: jcc invert 和 checked skip helper 风险最低；reverse deletion helper 次之；reg-state/alias tracking 不建议第一轮做, 容易把 pass-specific verifier safety 条件糊在一起。

没有运行 test/clippy/fmt；本次按要求只做 read-only source review 并写本报告。
