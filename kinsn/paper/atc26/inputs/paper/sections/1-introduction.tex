\section{Introduction}
\label{sec:introduction}

Extended Berkeley Packet Filter (eBPF) safely extends OS kernels and is widely used in production for networking~\cite{cilium,katran}, observability~\cite{bpftrace,bcc}, security~\cite{krsi_lwn,tracee}, and scheduling~\cite{sched_ext_lwn}.
% 扩展伯克利数据包过滤器（eBPF）安全地扩展操作系统内核，并在生产中被广泛使用，涵盖网络、可观测性、安全和调度等领域。
Its safety comes from a compilation pipeline that verifies every program before execution. In eBPF, a userspace compiler compiles each program to eBPF bytecode, the in-kernel verifier checks the bytecode for safety properties such as memory safety and termination, and the kernel's eBPF just-in-time compiler (the eBPF JIT) translates the verified bytecode to native code.
% 其安全性来自在执行前验证每个程序的编译管线：用户空间编译器将程序降低为 eBPF 字节码，内核验证器检查字节码的内存安全和终止性等安全属性，内核即时编译器（eBPF JIT）再将验证后的字节码翻译为本地代码。
The eBPF design favors safety over speed: the eBPF instruction set is designed to be verifiable and portable, and because the verifier checks only the bytecode, the kernel must trust the JIT and keeps it deliberately simple, translating one opcode at a time.
% eBPF 的设计偏重安全而非速度：eBPF 指令集是为可验证和可移植而设计的；而由于验证器只检查字节码，内核必须信任 JIT，因此刻意保持 JIT 简单，一次只翻译一个操作码。

However, this design comes at a cost.
% 这种设计是有代价的。
Many eBPF programs run on hot kernel paths where performance is critical, such as once for every packet, so even small slowdowns matter.
% \note{[zhengjie: breaking the logic. consider moving to para 1,] that will make however strange}
% 许多 eBPF 程序运行在内核热路径上，例如每个数据包运行一次，此时性能至关重要。
Compiled through the eBPF pipeline, the same C code takes up to twice as long to run as when compiled directly to native code (\S\ref{sec:characterization}).
% \note{For the same C source, code generated by the eBPF pipeline can take up to twice as long to execute as directly compiled native code (\S\ref{sec:characterization}).}
% 经过 eBPF 管线编译后，同样的 C 代码的运行时间最多是直接编译为本地代码时的两倍。
Because an optimizing compiler~\cite{zheng2025extending} fed the same verified bytecode recovers most of this gap, the loss lies in the eBPF JIT rather than in the bytecode itself.
% 由于对相同的验证字节码应用优化编译器可恢复大部分差距，损失在于eBPF JIT 的eBPF JIT，而不在字节码本身。

The clearest losses come from \emph{hardware idioms}, operations such as rotate, conditional select, and bit extract that a CPU usually executes as a single instruction but for which the eBPF instruction set has no single-instruction form.
% 最明显的损失来自\emph{硬件习语}：旋转、条件选择和位提取等操作，CPU 通常以单条指令执行它们，而 eBPF 指令集没有对应的单指令形式。
A 64-bit rotate with a variable shift, for example, is a single \texttt{ROL} instruction on x86-64, but it reaches the eBPF JIT as eight bytecode instructions and leaves as 15 machine instructions.
% 例如，64 位可变位移旋转在 x86-64 上是单条 ROL 指令，却以 8 条字节码指令到达eBPF JIT，并以 15 条机器指令离开。

You might think of three existing approaches, but they all fall short.
% 你可能会想到三种现有方案，但它们都有不足。
% \note{[zhengjie: Merlin and K2 are not intuitive approaches] Existing approaches to generating efficient native code for eBPF have several limitations.}
Optimizing on the bytecode still cannot emit the missing native instructions. Dedicated eBPF optimizers such as Merlin~\cite{mao2024merlin}, K2~\cite{xu2021synthesizing}, and EPSO~\cite{zhu2025epso} rewrite programs within the instruction set.
% 在字节码上优化无法发射缺失的指令：Merlin、K2 和 EPSO 等专用 eBPF 优化器只在指令集内重写程序。
Adding the missing instructions to the instruction set would require changing the compiler, the verifier, and the JIT for each architecture. Because the verifier and the JIT embody years of analysis and formal verification~\cite{nelson2020specification,vishwanathan2023verifying}, such changes are laborious and risk introducing safety bugs, so the instruction set has changed little since its standardization~\cite{rfc9669}.
% 在指令集中加入缺失的指令需要修改编译器、验证器和每个架构的 JIT；由于验证器和 JIT 凝聚了多年的分析和形式化验证，这样的修改既繁琐又容易引入安全漏洞，因此指令集自标准化以来几乎没有变化。
Optimizing during the translation from bytecode to native code, whether by replacing the simple JIT with an optimizing compiler or after verification~\cite{shahinfar2026fun}, would enlarge the trusted computing base (TCB) with a large compiler whose translation the kernel must trust, and, in the kernel, would also grow the code maintained for each architecture.
% 在从字节码翻译到本地代码的过程中进行优化，无论是用优化编译器替换简单的 JIT，还是在验证之后再优化，都会用一个内核必须信任其翻译的大型编译器扩大可信计算基（TCB），而放在内核中还会增加每个架构需要维护的代码。

To recover these losses, we must find a way for the simple eBPF JIT to emit native instructions that the instruction set lacks while keeping the TCB small.
% 要追回这些损失，我们必须找到一种方法，让简单的eBPF JIT 能发射指令集缺少的本地指令，同时保持 TCB 小。
Such instructions are many, since every architecture keeps adding instruction-set extensions, and which of them pay off depends on the CPU and the workload.
% 这样的指令很多：每个架构都在不断加入指令集扩展，而哪些扩展有收益取决于 CPU 和工作负载。
It must therefore be easy to add new operations, such as native instructions or functions, to eBPF.
% 因此，向 eBPF 添加新操作（例如本地指令或函数）必须容易。
% \note{[zhengjie:1. not coherent with the prev \& next sentence 2. similar to abstract, *new operation* is not clearly defined]}
Yet adding an operation safely must meet three requirements. First, the existing verifier must still prove every loaded program safe, even though new operations come from untrusted code outside the verifier and the JIT. Second, the kernel change must be small and made once rather than for every new operation. Third, although native code is specific to each architecture, the verifier's reasoning must remain architecture-independent.
% 然而，安全地添加一个操作必须满足三个要求：即使新操作来自验证器和 JIT 之外的不可信代码，现有验证器仍必须证明每个加载的程序安全；内核改动必须小，并且只做一次，而不是每增加一个操作就改一次；尽管本地代码特定于每个架构，验证器的推理必须保持与架构无关。

We present \tool, an extension interface that lets kernel modules introduce new operations without further kernel patches or verifier changes.
% 我们提出 \tool，一种扩展接口，让内核模块能够引入新操作，而无需再打内核补丁或修改验证器。
Our key insight is that a new operation can be verified through an equivalent vanilla eBPF form, while the CPU runs its native code.
% \note{same issue as in abstract}
% 我们的核心洞见是：新操作可以通过一个等价的原生 eBPF 形式来验证，而 CPU 运行它的本地代码。
\tool therefore gives each operation two forms: a \emph{proof sequence}, the vanilla (unextended) eBPF bytecode that the operation expands to for verification, and the native code that the JIT emits for it on each architecture.
% \note{[zhengjie] operation or extended bytecode?}
% \note{[zhengjie] form 1: (can be expanded to original) BPF bytecode; form 2: (can be emitted as) native code}
% 因此 \tool 给每个操作两种形式：原生（未扩展）eBPF 的\emph{证明序列}，和机器指令的\emph{本地代码}。
Because every proof sequence is vanilla eBPF, verification remains architecture-independent.
% 由于每个证明序列都是原生 eBPF，验证保持与架构无关。
A compile-time recognizer rewrites programs to use the new operations, and the verifier re-checks the proof sequences on every load.
% 编译时识别器重写程序以使用新操作，验证器在每次加载时重新检查证明序列。
Neither the recognizer nor the proof sequences are part of the TCB, because a wrong rewrite or proof sequence is either rejected by the verifier or yields a safe program that computes a different result.
% 识别器和证明序列都不属于 TCB，因为错误的改写或证明序列要么被验证器拒绝，要么产生一个计算结果不同但仍然安全的程序。
Since the verifier never sees an operation's native code, the code that generates it is the only code each operation adds to the TCB.
% 由于验证器从未看到本地代码，生成本地代码的代码是每个操作加入 TCB 的唯一代码。
We therefore prove in Lean 4 that, for each operation, the native code computes the same result as its proof sequence, which extends the verifier's guarantee to that code.
% \note{what is this trust gap?}
% 因此我们在 Lean 4 中证明，对于每个操作，本地代码与其证明序列计算相同的结果，从而将验证器的保证延伸到本地代码。
% We implement \tool in the Linux kernel and userspace tooling as a small, one-time kernel patch, a compile-time recognizer, and kernel modules that supply the operations.
% \note{repeat}

We implement \tool in Linux with a 929-line kernel patch.
% 我们用一个 929 行的内核补丁在 Linux 中实现 \tool。
Using \tool, we build \lang (extended Kernel  Instructions), a first set of seven hardware-idiom operations that programs use like new eBPF instructions, including rotate, conditional select, and bit extract.
% 借助 \tool，我们构建了 \lang，第一组七个硬件习语操作，程序像使用新的 eBPF 指令一样使用它们，包括旋转、条件选择和位提取。
On microbenchmarks, \lang speeds up eBPF programs by 24\% on x86-64 and 22\% on ARM64 in geometric mean over the unmodified pipeline, recovering 42\% of the x86-64 gap to native code, and it shrinks native code by 12--23\%.
% 在微基准测试上，\lang 相对未修改的管线使 eBPF 在 x86-64 上几何平均提速 24\%，在 ARM64 上提速 22\%，恢复了 x86-64 上与本地代码差距的 42\%，并使本地代码缩小 12--23\%。
On production applications, it improves throughput by up to 12\%. The gains are smaller because a real datapath spends most of its time in helper calls, map accesses, and tail calls, which instruction selection cannot reach (\S\ref{sec:eval}).
% 在生产应用上，它使吞吐量提高达 12\%；收益较小是因为真实数据通路的大部分时间花在 helper 调用、map 访问和尾调用上，这些是指令选择无法触及的。
The same interface also supports replacing whole programs with native code, which reaches 1.194$\times$ on Cilium when the application's entire native code is trusted and thus bounds the speedup that trusting more native code can bring (\S\ref{subsec:native_upper_bound}).
% \note{[zhengjie] on "bounds what a larger TCB can buy": trade for?}
% 同样的接口还支持整个程序的本地替换，在信任应用全部本地代码时在 Cilium 上达到 1.194 倍，从而给出了更大 TCB 所能换来的性能上限。

To summarize, we make the following contributions:
\begin{itemize}
    \item We characterize the performance gap between eBPF and native code and attribute it to the eBPF JIT, with the clearest losses from hardware idioms (\S\ref{sec:characterization}).
    \item We present \tool, an extension interface that adds new operations to the eBPF compilation pipeline (\S\ref{sec:mechanism}, and we build \lang, a set of seven hardware-idiom operations on top of it with lean 4 proves. (\S\ref{sec:lang}).
    \item Our implementation in the Linux kernel and userspace tooling (\S\ref{sec:implementation}) recovers 42\% of the x86-64 gap to native code (\S\ref{sec:eval}).\footnote{The artifact, with the microbenchmarks, the \tool and \lang implementations, the Lean proofs, and instructions for reproducing the experiments, is available at \url{https://github.com/eunomia-bpf/bpf-benchmark}.}
\end{itemize}
