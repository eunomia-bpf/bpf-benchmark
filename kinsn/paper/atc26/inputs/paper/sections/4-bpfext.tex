\section{\tool: Extending the eBPF Compilation Pipeline}
\label{sec:mechanism}
% \tool：扩展 eBPF 编译管线

\tool is designed to meet three requirements, which follow from the choice in \S\ref{subsec:char-challenges} to keep the simple eBPF JIT rather than add an optimizing compiler to the kernel.
% \tool 的设计要满足三个要求，它们来自 \S\ref{subsec:char-challenges} 的选择：保留简单的 eBPF JIT，而不是在内核中加入优化编译器。
First, the verifier must still prove every program safe, which keeps eBPF's existing guarantee unchanged (\S\ref{subsec:safety}).
% 第一，验证器必须仍然证明每个程序安全，从而保持 eBPF 现有的保证不变。
Second, supporting a new native instruction must not require rewriting the verifier or the JIT, which keeps the kernel change small and one-time (\S\ref{subsec:pipeline}).
% 第二，支持一条新的本地指令不得要求重写验证器或 JIT，从而使内核改动小且只做一次。
Third, the same computation may use a different native instruction on each architecture, while its verification stays architecture-independent (\S\ref{subsec:pipeline}).
% 第三，同一项计算在不同架构上可以使用不同的本地指令，而对它的验证保持与架构无关。

To meet them, \tool lets kernel modules add new operations to eBPF, each with a vanilla eBPF form for the verifier and native code for the CPU.
% 为满足这些要求，\tool 让内核模块向 eBPF 添加新操作，每个操作都有给验证器的原生 eBPF 形式和给 CPU 的本地代码。
\tool has three parts: a compile-time recognizer in userspace that rewrites programs to use new operations, kernel modules that supply each operation's two forms, and a one-time kernel patch that connects the operations to the verifier and the JIT.
% \tool 有三个部分：在用户空间改写程序以使用新操作的编译时识别器，提供每个操作两种形式的内核模块，以及把操作接入验证器和 JIT 的一次性内核补丁。
Figure~\ref{fig:pipeline} shows them at work on the rotate of \lang, the seven operations we build on \tool (\S\ref{sec:lang}): the recognizer turns the shifts and bitwise OR of a rotate into the \lang rotate, the kernel replaces it with its eBPF form for verification and restores it afterward, and the JIT emits its native code, a single rotate instruction.
% 图~\ref{fig:pipeline} 以 \lang（我们在 \tool 上构建的七个操作，\S\ref{sec:lang}）中的旋转为例展示它们如何协作：识别器把旋转的移位和按位或变成 \lang 旋转，内核在验证时把它替换为 eBPF 形式并在之后恢复，JIT 发射它的本地代码，即一条旋转指令。
\S\ref{subsec:pipeline} follows this pipeline in detail, \S\ref{sec:lang} presents \lang, and \S\ref{subsec:safety} argues that the extended pipeline keeps eBPF safe.
% \S\ref{subsec:pipeline} 详细走一遍这条流水线，\S\ref{sec:lang} 介绍 \lang，\S\ref{subsec:safety} 论证扩展后的流水线保持 eBPF 的安全。

\subsection{Operations and the Compilation Pipeline}
\label{subsec:pipeline}
% 操作与编译管线

An operation in \tool has two forms with the same semantics: a \emph{proof sequence} written in vanilla eBPF, which the verifier checks, and native code for each architecture, which the CPU runs.
% \tool 中的一个操作有两种语义相同的形式：用原生 eBPF 写成、由验证器检查的\emph{证明序列}，以及每个架构上由 CPU 运行的本地代码。
Because the verifier sees only the proof sequence, it needs no new semantics for any operation, and its existing analysis checks them all.
% 由于验证器只看到证明序列，它不需要为任何操作增加新语义，现有的分析就能检查所有操作。
A program uses an operation by naming it, together with its operands, in place of the eBPF code it replaces.
% 程序在原来那段 eBPF 代码的位置写上操作的名字及其操作数，以此使用该操作。

To run such a program, the pipeline handles each operation in three stages: recognition in userspace, verification in the kernel on its proof sequence, and code generation by the JIT from its native code.
% 为了运行这样的程序，流水线分三个阶段处理每个操作：用户空间中的识别、内核中基于证明序列的验证，以及 JIT 基于本地代码的代码生成。
In userspace, before the program loads, the recognizer matches the patterns of supported operations (\S\ref{subsec:llvm}) and rewrites each match into one operation, or into more than one when an architecture splits the idiom (\S\ref{sec:lang}).
% 在用户空间、程序加载之前，识别器匹配所支持操作的模式（\S\ref{subsec:llvm}），把每处匹配改写成一个操作；当某个架构把该习语拆开时，则改写成多个操作。
For the rotate, the pattern is the shift-and-or sequence of Figure~\ref{fig:jit-dump}.
% 对于旋转，模式就是图~\ref{fig:jit-dump} 中的移位加按位或序列。
In Figure~\ref{fig:pipeline}, it rewrites the shifts and bitwise OR of a 64-bit left rotate by 16 (\ding{172}) into a \lang rotate whose operands name \texttt{r7} as source and destination and 16 as the rotate amount (\ding{173}).
% 在图中，它把 64 位左旋 16 位的移位和按位或（①）改写为一条操作，其操作数指定 r7 为源和目的、16 为旋转量（②）。

In the kernel, before the verifier's analysis runs, the kernel patch replaces each operation in the program with its proof sequence, so the analysis sees only vanilla eBPF (\ding{174}).
% 在内核中，验证器分析运行之前，内核补丁把程序中的每个操作替换为它的证明序列，使分析只看到原生 eBPF（③）。
Once the analysis accepts the program, the patch restores the operations (\ding{175}) so that the JIT can emit their native code.
% 分析接受程序后，补丁恢复这些操作（④），使 JIT 能够发射它们的本地代码。
Restoring them right after the analysis also lets the kernel's rewriting passes that follow verification and prepare the program for the JIT handle each operation as an ordinary eBPF instruction.
% 在分析之后立即恢复，也让验证之后、为 JIT 准备程序的内核改写步骤能把每个操作当作普通的 eBPF 指令处理。

During code generation, the JIT replaces each operation with its native code for the running architecture, through one case that the kernel patch adds.
% 在代码生成时，JIT 通过内核补丁加入的一个分支，用当前架构上的本地代码替换每个操作。
For the \lang rotate, it emits a single \texttt{ROL} on x86-64, here \texttt{rol r13, 16} with \texttt{r13} holding eBPF register \texttt{r7} (\ding{176}), or a single \texttt{ROR} on ARM64.
% 对于 \lang 旋转，它在 x86-64 上发射一条 ROL，这里是 rol r13, 16，其中 r13 存放 eBPF 寄存器 r7（⑤），在 ARM64 上发射一条 ROR。
When an operation has no native code for the architecture, it falls back to its proof sequence, which the JIT compiles as vanilla eBPF.
% 当一个操作在该架构上没有本地代码时，它回退到证明序列，由 JIT 作为原生 eBPF 编译。
Because the interpreter cannot run native code, a kernel without a JIT rejects programs that use operations.
% 由于解释器无法运行本地代码，没有 JIT 的内核会拒绝使用操作的程序。

The same program thus verifies as vanilla eBPF and runs as native code, with only three additions to the kernel: a step before the verifier's analysis, a step after it, and a case in the JIT.
% 于是同一程序作为原生 eBPF 验证、作为本地代码运行，而内核只需增加三处：验证器分析之前的一步、之后的一步，以及 JIT 中的一个分支。
These additions meet the second requirement: none of them depends on a particular operation or changes the verifier's analysis or how the JIT translates ordinary instructions (\S\ref{subsec:kernel}), so a new operation needs only a pattern in the recognizer and one or more kernel modules that supply its proof sequence and native code.
% 这些新增满足第二个要求：它们都不依赖于特定操作，也都不改变验证器的分析或 JIT 对普通指令的翻译，因此新操作只需要识别器中的一个模式，以及一个或多个提供其证明序列和本地代码的内核模块。
The third requirement holds as well: even when an operation's proof sequence differs across architectures (\S\ref{sec:lang}), every variant is vanilla eBPF checked by the same analysis.
% 第三个要求同样满足：即使一个操作的证明序列在不同架构上不同，每种变体也都是由同一分析检查的原生 eBPF。

\subsection{\lang: Hardware-Idiom Operations}
\label{sec:lang}
% \note{[zhengjie, Overleaf] on the subsection title: Extended eBPF Bytecode?}
% \lang：硬件习语操作

\lang is a first set of seven operations built on \tool.
% \lang 是基于 \tool 构建的第一组七个操作。
We chose them from the networking, tracing, and security workloads of \S\ref{sec:characterization}, where the clearest losses come from hardware idioms that the eBPF instruction set cannot express as a single instruction, such as rotate and conditional select.
% 我们从 \S\ref{sec:characterization} 的网络、追踪和安全类工作负载中挑选了它们，这些负载中最明显的损失来自 eBPF 指令集无法用单条指令表达的硬件习语，例如旋转和条件选择。
Such idioms are few (\S\ref{subsec:char-idiom}), so a handful of operations covers these losses.
% 这类习语很少（\S\ref{subsec:char-idiom}），因此少数几个操作就能覆盖这些损失。
Each \lang operation covers one idiom with its variants, such as the 64-bit and 32-bit rotate, and its kernel modules implement each variant, whether it differs in width, condition, or architecture, separately.
% 每个 \lang 操作覆盖一个习语及其变体，例如 64 位和 32 位旋转，它的内核模块分别实现每个变体，无论变体在宽度、条件还是架构上不同。
Other workloads, such as schedulers, may need different instructions, which can be added as kernel modules without changing the kernel patch.
% 其他工作负载（如调度器）可能需要不同的指令，它们可以作为内核模块加入，而无需修改内核补丁。

Table~\ref{tab:descriptors} lists the seven operations with their proof sequences and their native code on x86-64 and ARM64.
% 表~\ref{tab:descriptors} 列出了这七个操作及其证明序列和在 x86-64 与 ARM64 上的本地代码。
Six of them replace fixed bytecode patterns, which the recognizer matches and rewrites in place.
% 其中六个替换固定的字节码模式，识别器原地匹配并改写它们。
The prefetch is the exception: it has no eBPF equivalent, so the recognizer inserts it at sites it selects, and its proof sequence is a no-op.
% 预取是例外：它没有 eBPF 等价物，因此识别器在自己选择的位置插入它，其证明序列是空操作。

Because native code is specific to each architecture, the same idiom may need a different number of \lang operations on each architecture, or have none on some.
% 由于本地代码特定于每个架构，同一习语在不同架构上可能需要不同数量的 \lang 操作，在某些架构上也可能没有对应操作。
A conditional select, for example, is one \lang operation on x86-64, emitting the \texttt{CMP+CMOV} pair, but two on ARM64, one emitting \texttt{TST} and one emitting \texttt{CSEL}.
% 例如，条件选择在 x86-64 上是一个 \lang 操作，发射 CMP+CMOV 指令对，在 ARM64 上则是两个，一个发射 TST，一个发射 CSEL。
The byte swap of a loaded value splits the same way on ARM64, into an \texttt{LDR} and a \texttt{REV}, and the address computation \texttt{LEA} exists on x86-64 alone.
% 加载值的字节交换在 ARM64 上同样拆分为 LDR 和 REV，而地址计算 LEA 只存在于 x86-64。
The recognizer therefore rewrites a program for the architecture it will load on.
% 因此识别器针对程序将要加载的架构来改写程序。

\subsection{Safety and the Trusted Computing Base}
\label{subsec:safety}
% 安全性与可信计算基

We assume that programs and the recognizer may be buggy or malicious, while the kernel code that \tool adds, namely its patch and the operation modules, must be free of ordinary bugs like any other kernel code.
% 我们假设程序和识别器可能有错甚至恶意，而 \tool 新增的内核代码，即补丁和操作模块，与其他内核代码一样必须没有普通错误。
Under this assumption, safety rests on two arguments: the verifier checks everything \tool adds to a program except an operation's native code, and that native code is proved to compute the same result as its proof sequence.
% 在这一假设下，安全性基于两点论证：验证器检查 \tool 加入程序的一切，唯独操作的本地代码除外，而这些本地代码被证明与其证明序列计算出相同结果。
For the first argument, the recognizer's rewrites and the modules' proof sequences all end up in the program that the verifier checks on every load, with the same analysis as for vanilla eBPF.
% 就第一点而言，识别器的改写和模块提供的证明序列最终都进入验证器每次加载时检查的程序，并接受与原生 eBPF 相同的分析。
A rewrite or proof sequence that violates safety therefore fails verification like any unsafe program, so a wrong rewrite is either rejected or yields a safe program that computes a different result, and the userspace recognizer lies outside the TCB.
% 因此违反安全的改写或证明序列会像任何不安全的程序一样无法通过验证，错误的改写要么被拒绝，要么产生一个计算结果不同但安全的程序，所以用户空间识别器不在 TCB 之内。

One gap remains in the first argument: the verifier checks the program with proof sequences, but the JIT compiles the program with the operations, so what the verifier proves about the first must also hold for the second.
% 第一点论证还有一个缺口：验证器检查的是含证明序列的程序，而 JIT 编译的是含操作的程序，因此验证器对前者证明的性质必须对后者同样成立。
The two programs differ only where a proof sequence stands in for its operation, so the verifier's conclusions carry over as long as each proof sequence behaves like a single instruction: control enters it only at its top and leaves only past its end.
% 两个程序只在证明序列代替操作的地方不同，因此只要每个证明序列表现得像单条指令，即控制流只从顶部进入、只从末尾之后离开，验证器的结论就能延续下来。
To enforce this, the kernel validates, before the verifier's analysis, that each proof sequence has a single entry and a single exit and contains no nested operations, calls, exits, or backward jumps.
% 为此，内核在验证器分析之前验证每个证明序列单入口、单出口，且不含嵌套操作、调用、退出或向后跳转。
A proof sequence also borrows no scratch registers or stack slots, so it writes only the registers and memory that the operation itself writes, and the kernel need not check which registers the code after it still reads.
% 证明序列也不借用任何临时寄存器或栈槽，因此它只写操作本身会写的寄存器和内存，内核也就无需检查其后的代码还会读取哪些寄存器。

What remains trusted is the existing eBPF verifier and JIT, together with \tool's one-time kernel patch around them, which validates proof sequences, replaces operations with their proof sequences before verification, restores them afterward, and emits their native code (\S\ref{sec:implementation}).
% 仍需信任的是现有的 eBPF 验证器和 JIT，以及 \tool 围绕它们的一次性内核补丁，它验证证明序列，在验证前把操作替换为证明序列，之后恢复，并发射本地代码。
Beyond these one-time components, only an operation's native code escapes any check at load time.
% 除了这些一次性组件，只有操作的本地代码不受任何加载时检查。
Each operation must therefore supply evidence that its native code computes the same result as its proof sequence on every register and memory location.
% 因此每个操作必须提供证据，证明其本地代码在每个寄存器和内存位置上与证明序列计算出相同的结果。

\label{sec:formal-verification}
For the second argument, we prove in Lean 4 that the two forms of each \lang operation agree.
% 就第二点而言，我们在 Lean 4 中证明每个 \lang 操作的两种形式一致。
We model each eBPF and native instruction by its effect on registers and memory, and a sequence by applying these effects in order. We write the eBPF and x86-64 models ourselves, and the ARM64 models follow LNSym~\cite{lnsym}.
% 我们用每条 eBPF 指令和本地指令对寄存器和内存的作用为其建模，并按顺序施加这些作用来为指令序列建模；eBPF 和 x86-64 模型由我们自己编写，ARM64 模型沿用 LNSym。
The proofs assume that the verifier has accepted the proof sequence and that the initial state is one the verifier considers safe.
% 证明假设验证器已经接受了证明序列，并且初始状态是验证器认为安全的状态。
Under these models, the two forms of register-only \lang operations such as rotate, conditional select, and bit extract must agree on the destination register and leave every other register unchanged. For \lang operations that access memory, such as the byte swap of a loaded value and bulk copy, they must also agree on the accessed memory and leave all other memory unchanged.
% 在这些模型下，仅寄存器的 \lang 操作（如旋转、条件选择和位提取）的两种形式必须在目标寄存器上一致，并保持其他所有寄存器不变；对于访问内存的 \lang 操作，如加载值的字节交换和批量拷贝，它们还必须在访问的内存上一致，并保持其他内存不变。
Prefetch is modeled as an architectural no-op, and microarchitectural effects such as cache state are outside the model.
% 预取被建模为体系结构层面的空操作，缓存状态等微体系结构效应不在模型之内。

The proof connects the two forms through a hardware-independent specification of each operation.
% 证明通过每个操作的一个与硬件无关的规范把两种形式联系起来。
For the \lang rotate, the specification is $\operatorname{rotl}_{64}(x,n)=(x\ll n)\lor(x\gg(64-n))$ for $1\leq n<64$, over 64-bit bit-vectors with a logical right shift.
% 对于旋转，规范是 64 位位向量上的 rotl64(x,n)=(x<<n)|(x>>(64-n))，1<=n<64，右移为逻辑右移。
One lemma shows that the proof sequence, which rotates the destination register left by one bit $n$ times (a left shift by one that sets the low bit when the sign bit was set), leaves $\operatorname{rotl}_{64}(x,n)$ in its destination register, and a second lemma, one per architecture, shows the same for the native \texttt{ROL} on x86-64 and \texttt{ROR} (encoded as \texttt{EXTR}) on ARM64.
% 一条引理表明证明序列（把目标寄存器循环左移一位，重复 n 次：左移一位，若原符号位为 1 则把最低位置 1）在其目标寄存器中留下 rotl64(x,n)，另一条引理（每个架构一条）对 x86-64 上的 ROL 和 ARM64 上的 ROR（编码为 EXTR）给出同样的结论。
Because both results equal the specification, the destination registers agree, and register-preservation lemmas show that neither form changes any other register.
% 两个结果都等于规范，因此目标寄存器一致；寄存器保持引理表明两种形式都不改变任何其他寄存器。
Each \lang operation is proved the same way.
% 每个 \lang 操作都以同样的方式证明。

The proofs trust only the instruction models and Lean itself.
% 这些证明只信任指令模型和 Lean 本身。
No translation between the two instruction sets is needed: both are modeled in one Lean development and meet only in the specification, which need not be trusted, since the lemmas give equality whatever it says.
% 两套指令集之间不需要任何翻译：它们在同一个 Lean 开发中建模，只在规范处相遇；规范无需信任，因为无论规范是什么，引理都给出相等。
That the functions generating native code emit exactly the modeled instructions is checked separately (\S\ref{subsec:descriptors}).
% 生成本地代码的函数是否恰好发射建模的指令，另行检查（\S\ref{subsec:descriptors}）。
Because the proofs are checked offline, an operation's developers check them once, and those who deploy it trust its module as they would any other kernel module.
% 由于证明在离线检查，操作的开发者只需检查一次，部署者像信任任何其他内核模块一样信任它的模块。

The proofs extend to new operations and architectures with little new work, because the instruction models and register-preservation lemmas are shared across operations, and each \lang operation replaces only a small fragment of a program, so its proof stays small.
% 证明可以以很少的新工作扩展到新操作和新架构，因为指令模型和寄存器保持引理在各操作之间共享，而且每个 \lang 操作只替换程序中的一小段，所以它的证明也很小。
A new operation on an existing architecture needs only its specification and its two lemmas.
% 现有架构上的新操作只需要它的规范和两条引理。
A new architecture needs a model of its native instructions and proofs that its native code computes the existing specifications, while the lemmas for existing proof sequences carry over unchanged.
% 新架构需要其本地指令的模型，以及其本地代码计算现有规范的证明，而现有证明序列的引理无需修改即可沿用。
\tool itself leaves an operation's size open: within the rules above, a proof sequence may span a few instructions or a larger part of the program, at the cost of a larger proof.
% \tool 本身不限制操作的大小：在上述规则之内，证明序列可以只有几条指令，也可以覆盖程序中更大的部分，代价是更大的证明。
